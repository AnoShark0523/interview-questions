④ 技术栈实现流程与原理

网络通信流程：

客户端发起 TCP 连接 → JSON 封装请求（操作类型 + 参数）→ 服务端解析 JSON → 查询/写入 SQLite → JSON 响应返回 → 客户端解析更新 UI

视频解码流程（三线程模型）：

1. 读包线程（QThread）：FFmpeg 打开视频 → av_read_frame 循环读压缩包 → 按流索引分发到视频/音频 PacketQueue

2. 视频解码线程（SDL 创建）：从视频队列取包 → avcodec_send_packet + avcodec_receive_frame 解码 → YUV 转 RGB → Qt 信号槽通知主线程 → OpenGL 上传纹理渲染

3. 音频回调线程（SDL 内部）：注册回调函数 → SDL 按采样率自动回调 → 从音频队列取包解码 → 填充播放缓冲区

音视频同步原理：

以音频 PTS 为主时钟 → 视频帧解码后对比 PTS → 视频快了延迟显示 → 视频慢了丢帧追赶。选音频主时钟是因为音频不能变速（会变调），视频可以丢帧。

硬件解码流程：

初始化时尝试创建 DXVA2 硬件解码设备上下文 → 成功则走硬解路线 → GPU 不支持该格式时创建失败 → 自动回退 FFmpeg 软解码兜底

VA项目 - 音视频播放核心

Q1 三线程解码结构？音频回调怎么触发？

三个线程各司其职：

1. 读包线程（继承 QThread）：从文件/网络读压缩数据包，根据流索引分别放入视频队列和音频队列

2. 视频解码线程（SDL 创建）：从视频队列取包，解码出 YUV 帧，转 RGB 后通过 Qt 信号槽通知主线程更新画面

3. 音频回调线程（SDL 内部线程）：注册回调函数后，SDL 底层按音频设备采样率定期回调，回调里从音频队列取数据解码后填充播放缓冲区

回调触发：SDL 音频设备驱动按设定采样率自动调用，不需要手动触发。

Q2 音视频同步怎么实现的？

以音频时钟为主时钟。

1. 音频播放时，每解码一帧就更新音频时钟（记录当前音频时间戳）

2. 视频帧解码后，比较视频时间戳和音频时间戳

3. 视频比音频快 → 延迟显示（等一等）

4. 视频比音频慢 → 丢帧（跳过当前帧，赶紧追）

为什么选音频主时钟？ 音频不能变速播放（会变调），视频可以丢帧/延迟来追音频。

Q3 视频慢了怎么追赶？时钟靠什么更新？

时钟更新：基于时间戳（PTS）驱动更新，而非定时器。定时器是阶梯式的、频率和实际解码速度不一定匹配；基于时间戳的更新跟随实际数据流，更精确。

追赶策略：丢帧追赶——直接丢弃过时的视频帧不渲染，继续解码下一帧。连续丢几帧后追上。视频丢帧用户几乎感知不到，但音频断续很明显。

Q4 四级播放缓存策略是什么？

从高到低依次尝试：

1. 本地路径：文件在本地，直接播放，最快

2. 本地缓存：之前下载过，从缓存目录读，避免重复下载

3. 服务器下载：通过 HTTP 下载，FFmpeg 支持 HTTP URL 边下边播

4. 文件选择对话框：以上都失败，弹出选择框让用户手动选

Q5 为什么用 FFmpeg+SDL2 不用 Qt 自带播放器？

1. 解码能力强：FFmpeg 支持几乎所有视频格式，Qt 自带播放器依赖系统解码器，格式受限

2. 支持硬件加速：FFmpeg 支持硬件解码，Qt 自带播放器控制力弱

3. 同步控制精细：FFmpeg 可以直接访问时间戳和帧数据，Qt 封装太深

4. 自定义渲染：配合 OpenGL 可以实现自定义渲染效果

5. 网络流播放：FFmpeg 原生支持直接播放 HTTP URL

Q6 OpenGL 纹理映射怎么实现视频渲染？

把视频帧数据上传到 GPU 纹理，画一个全屏四边形把纹理贴上去。

1. 创建 OpenGL 纹理对象

2. 把解码出的 RGB 数据上传到纹理

3. 顶点着色器定义四个顶点构成全屏矩形（两个三角形）

4. 片段着色器从纹理采样颜色值

5. 绘制

为什么用 OpenGL？ GPU 并行处理像素，比 CPU 软渲染快很多。项目中用 Qt 的 OpenGL 组件承载渲染，SDL 只管音频，避免资源争抢。

Q7 硬件解码是什么？怎么自动回退软解码？

硬件解码：利用 GPU 专用解码单元解码视频，CPU 几乎零负载。软解码全靠 CPU 算力，4K 视频会卡；硬解码交给 GPU，CPU 占用极低，更省电更流畅。

自动回退机制：

1. 初始化时尝试创建硬件解码设备上下文

2. 如果 GPU 不支持该编码格式，创建失败

3. 自动切换到 FFmpeg 软件解码

4. 硬解码后需要把帧从 GPU 显存拷回 CPU 内存才能渲染

5. 对用户透明，用户感觉不到区别

Q8 倍速播放怎么实现？音频怎么变速不变调？

视频：靠跳帧。2倍速时每2帧只显示1帧，奇数帧跳过不渲染。

音频：用 WSOLA 算法（波形相似叠加时域压缩）——把音频切成小段重叠拼接，去掉重叠部分，时间变短但频率不变，音调不变。直接加快采样率会让声音变尖，所以不能用那种方法。

同步：倍速后音视频时间戳都除以倍率，保证同步关系不变。

项目支持 0.5x / 1.0x / 1.25x / 1.5x / 2.0x 五档变速。

Q9 为什么 SDL 视频模块和 Qt 冲突？

SDL 的视频模块会创建独立的 SDL 窗口和事件循环，和 Qt 的事件循环争抢系统消息（Windows 消息队列），导致 Qt 窗口鼠标点击/重绘失效。

解决方案：只初始化 SDL 的音频模块，视频渲染交给 Qt 的 OpenGL 组件。各司其职——SDL 管音频，Qt/OpenGL 管视频。

Q10 网络播放和本地播放有什么区别？

网络播放的核心是初始化网络模块后，FFmpeg 可以直接接受 HTTP URL。

FFmpeg 内部自动建立 TCP 连接、发送 HTTP 请求、接收数据。后续解码流程和本地播放完全一样——打开流 → 找解码器 → 解码。

区别只是数据来源不同：本地是文件读取，网络是 HTTP Range 请求。

Q11 编码和解码的 API 对应关系？

| 方向 | 解码 | 编码 | |---|---|---| | 输入 | 压缩包 | 原始帧 | | 输出 | 原始帧 | 压缩包 | | API | 送压缩包 → 取原始帧 | 送原始帧 → 取压缩包 |

两者正好对称反过来。项目里解码用于播放视频，编码用于录制视频。

Q12 FFmpeg 编码流程？项目用它做什么？

项目用编码实现录制视频功能，输出 H.264+AAC 的 FLV 文件。

流程：创建输出格式 → 查找编码器 → 创建输出流 → 设置编码参数 → 打开编码器 → 循环送入原始帧取出压缩包 → 交错写入文件 → 写文件尾。

Q13 交错写入和直接写入有什么区别？

- 直接写入：不保证音视频包交错，可能先写完所有视频包再写音频包

- 交错写入：内部维护缓冲队列，按时间戳排序后交错写入，音视频包按时间顺序排列，播放器可以边下边播

项目录制视频时用交错写入，保证输出的 FLV 文件音视频交错，播放器能正常播放。

Q14 项目中用到滤镜了吗？

没有使用滤镜。

原因：项目是播放平台不是编辑软件，滤镜不是刚需；滤镜会在解码后渲染前插入处理环节，增加延迟；保持解码→格式转换→渲染的直通管线，调试简单；项目追求播放流畅性，滤镜每帧增加几毫秒延迟影响体验。

Q15 从打开视频到显示第一帧画面的完整流程？

1. 注册网络模块：如果是网络播放，先初始化 FFmpeg 网络模块

2. 打开文件/URL：用 FFmpeg 打开文件或 HTTP 地址，得到格式上下文

3. 分析流信息：调用方法分析文件格式、编码格式、分辨率、帧率等

4. 找到音视频流索引：遍历所有流，找到视频流和音频流的索引号

5. 查找解码器：根据流信息中的编码 ID 查找对应的解码器

6. 打开解码器：创建解码器上下文，设置参数后打开解码器

7. 初始化 SDL 音频：设置采样率、声道数、采样格式，注册回调函数，打开音频设备

8. 初始化 OpenGL：创建纹理对象，准备着色器

9. 启动读包线程：循环读取压缩包，根据流索引放入视频队列或音频队列

10. 启动解码线程：视频解码线程从队列取包解码，音频解码在 SDL 回调中执行

11. 第一帧显示：视频解码线程解码出第一帧，转 RGB 上传纹理，通过信号槽通知主线程渲染

Q16 你说用 FFmpeg 解码，具体流程能说一下么？

解码核心就是一个循环：送压缩包进去，取原始帧出来。

1. 从队列取压缩包：读包线程把压缩包放入队列，解码线程从队列取出

2. 发送压缩包到解码器：调用发送函数把压缩包送入解码器内部缓冲区

3. 接收解码后的帧：调用接收函数取出解码后的原始帧（YUV 格式）

4. 一个包可能解出多帧：需要循环接收直到没有帧返回

5. 像素格式转换：把 YUV 转成 RGB（因为 OpenGL 渲染需要 RGB）

6. 上传纹理：把 RGB 数据上传到 GPU 纹理

7. 音视频同步判断：比较当前帧的时间戳和音频时钟，决定立即显示、延迟显示还是丢帧

8. 通知渲染：通过信号槽通知主线程更新画面

Q17 PacketQueue 具体怎么实现的？为什么用条件变量？

PacketQueue 是一个线程安全的阻塞队列，是生产者-消费者模式的核心。

数据结构：内部用一个标准队列存储压缩包，配合互斥锁和条件变量。

核心操作：

- 入队（生产者）：加锁 → 数据放入队列 → 通知条件变量（唤醒等待的消费者）→ 解锁

- 出队（消费者）：加锁 → 队列空就条件变量等待（阻塞，释放锁）→ 被唤醒后取数据 → 解锁

为什么用条件变量不用轮询？ 轮询需要不断循环检查队列是否为空，浪费 CPU 资源。条件变量让线程在队列为空时自动睡眠，有数据时被生产者唤醒，CPU 占用几乎为零。

为什么有上限？ 队列设了最大长度，防止读包太快把内存撑爆。满了之后读包线程阻塞等待，消费者取走后再唤醒。

Q18 OpenGL 着色器怎么写的？YUV 转 RGB 在哪做？

YUV 转 RGB 在 CPU 端做，不是在着色器里做。项目用 FFmpeg 的缩放和格式转换库在 CPU 端把 YUV 转成 RGB，然后上传 RGB 到纹理。

着色器很简单：

- 顶点着色器：定义四个顶点构成全屏矩形（两个三角形），传递纹理坐标

- 片段着色器：从纹理采样 RGB 颜色值，直接输出

Q19 硬件解码初始化失败后具体怎么检测和切换的？

1. 尝试创建硬件解码设备上下文：根据平台选择对应的硬件加速类型（Windows 上用 DXVA2）

2. 绑定到解码器上下文：把硬件设备上下文设置到解码器上下文中

3. 打开解码器：尝试打开，如果 GPU 不支持该编码格式，打开会失败

4. 检测失败：捕获返回值，如果小于 0 表示失败

5. 清理硬件上下文：释放硬件设备上下文相关资源

6. 切换到软件解码：重新查找软件解码器，用纯软件方式打开

7. 设置标志位：标记当前是软解码模式，后续解码流程统一处理

硬解码的特殊处理：硬解输出的帧在 GPU 显存里，需要通过数据传输函数把帧从显存拷贝到 CPU 内存，才能做格式转换和渲染。软解码直接输出在 CPU 内存，不需要这一步。

Q20 视频录制编码管线怎么串联的？

录制功能把摄像头画面和麦克风声音编码成一个 FLV 文件。

1. 初始化摄像头采集：用 OpenCV 或系统 API 采集摄像头画面帧

2. 初始化音频采集：用 SDL 采集麦克风音频数据

3. 创建输出格式上下文：指定输出格式为 FLV

4. 创建视频编码器：查找 H.264 编码器，创建视频流，设置分辨率、帧率、码率参数

5. 创建音频编码器：查找 AAC 编码器，创建音频流，设置采样率、声道数参数

6. 打开编码器：分别打开视频和音频编码器

7. 编码循环：采集到一帧画面 → 送入视频编码器 → 取出压缩包 → 交错写入文件；采集到一段音频 → 送入音频编码器 → 取出压缩包 → 交错写入文件

8. 写文件尾：录制结束时写文件尾，确保文件完整

关键点：用交错写入保证音视频包按时间顺序排列，播放器能正常播放。

VA项目 - 网络通信与上传

Q21 TCP 通信和链式上传怎么设计的？

通信协议：自定义 TCP 协议，格式 = 4字节长度头 + JSON 数据体。用 NetworkManager 单例统一管理连接。

链式上传：视频上传分三步串行执行——先传视频文件（分块64KB），再传封面图片，最后传元数据。

为什么串行？ 防止数据交错。并行发三种数据混在一起，服务器分不清哪段是文件哪段是元数据。

Q22 视频上传为什么要分块传输？

1. 大文件内存问题：一次性读整个视频到内存，几百MB 会爆内存。分块每次只占小内存

2. 断点续传：传到一半断了，下次从断点继续

3. 进度反馈：每传一块更新进度条

4. 网络稳定性：某一块失败只需重传这一块

Q23 断点续传怎么做的？

核心：记录已传输位置，断线重连后从断点继续。

1. 上传前，客户端先问服务器"这个文件传到哪了"（发文件 MD5 + 文件名）

2. 服务器返回已传输字节数

3. 客户端跳到断点位置继续读数据发送

4. 服务器在文件末尾追加写入

秒传：服务器发现文件 MD5 已存在，直接返回"已存在"，0 字节传输完成。

Q24 HTTP 渐进式流是什么？服务器怎么实现？

用户边下载边播放，不需要等整个视频下载完。

核心：HTTP Range 请求。客户端请求某个字节范围，服务器只返回这个范围的数据。

服务器实现：解析请求头中的 Range 字段 → 定位到对应偏移量 → 只读取请求范围的字节返回 → 设置响应头。

Q25 双端口设计是什么？

- 8080端口：业务通信，TCP Socket + JSON，处理登录/注册/元数据查询

- 8081端口：HTTP 流媒体，支持 Range 请求，专门传输视频数据

分开原因：避免业务消息和视频数据互相阻塞——视频数据量大，共用连接会导致实时消息被淹没延迟。

Q26 为什么不用 RTMP 或 HLS？

- RTMP：直播协议，需要专门服务器，项目是点播不是直播

- HLS：苹果的切片流协议，需要把视频切成小段，实现复杂且有延迟

- HTTP 渐进式流：最简单直接，Range 请求就能边下边播，FFmpeg 原生支持，够用

Q27 服务端处理一次请求的完整流程？

1. 接受客户端连接

2. 先读 4 字节长度头，再按长度读完整 JSON 数据体

3. 解析 JSON，提取类型字段判断请求类型

4. 根据类型调用对应处理函数

5. 业务处理（查数据库/读写文件）

6. 把结果打包成 JSON，加 4 字节长度头

7. 发回客户端

8. 关闭连接或保持长连接

Q28 有没有做网络防抖设计？

1. 本地缓存机制：四级播放策略优先播放本地缓存

Q31 我看你有视频上传，具体怎么实现的？

视频上传采用链式分块传输，分三步串行完成：

第一步：上传视频文件

1. 客户端发 JSON 通知服务器"准备接收文件"，包含文件名、文件大小、MD5

2. 服务器检查 MD5，如果已存在直接返回"秒传成功"

3. 服务器返回已传输字节数（断点续传）

4. 客户端从断点位置开始，每次读 64KB 发送

5. 每发一块更新进度条

6. 服务器追加写入文件，返回当前已接收字节数

7. 直到全部发完

第二步：上传封面图片 - 视频文件传完后，用同样的分块方式传封面图片

第三步：上传元数据 - 封面传完后，发一条 JSON 包含标题、描述、作者 ID、标签等，服务器把元数据写入数据库

为什么 64KB？ 太小（如 1KB）会导致发送次数太多、TCP 头部开销大；太大（如 1MB）内存占用高、单块失败重传成本大。64KB 是网络传输的常用平衡点。

Q32 HTTP 流媒体服务器具体代码怎么处理的？

服务器在 8081 端口监听 HTTP 请求，核心是处理 Range 请求头：

1. 接收 HTTP 请求：解析请求行（GET /video/xxx.mp4）和请求头

2. 解析 Range 头：读取 Range: bytes=0-1048575 这样的字段，提取起始和结束位置

3. 打开视频文件：根据请求路径找到服务器上的视频文件

4. 定位到偏移量：用文件 seek 操作跳到请求的起始字节

5. 读取指定范围：只读取 Range 请求的字节数

6. 构造 HTTP 响应：状态码 206（Partial Content）、Content-Range、Content-Length、Accept-Ranges: bytes

7. 发送响应头 + 数据体

没有 Range 头时：返回状态码 200，发送整个文件。

Q33 TCP 长度头具体读写逻辑是什么？

发送端：

1. 把数据序列化成 JSON 字符串

2. 计算 JSON 字符串的字节长度 N

3. 先发 4 字节的长度头（N 的大端序表示）

4. 再发 N 字节的 JSON 数据体

接收端：

1. 循环读直到读满 4 字节，解析出长度 N

2. 循环读直到读满 N 字节，得到完整 JSON 数据体

3. 解析 JSON，处理请求

为什么要循环读？ TCP 是流式协议，一次 recv 不一定能读够需要的字节数。

大端序：网络字节序统一用大端序，保证不同机器之间的通信正确。

Q40 Agent 和 LLM 的区别？

- LLM（大语言模型）：就是一个模型，给它文本它输出文本，没有自主性，不会调工具

- Agent（智能体）：以 LLM 为大脑，加上感知、决策、行动能力，能自主规划任务、调用工具、根据反馈调整

项目应用：视频内容理解 Agent（抽帧→看图→生成摘要），智能推荐 Agent（向量化→检索→生成推荐理由）

Q41 RAG 是什么？实现流程？

RAG（检索增强生成）：让模型"先查资料再回答"，答案有据可依。

流程：文档切块 → 每块转向量 → 存入向量数据库 → 用户提问也转向量 → 检索最相似的几块 → 把检索结果+问题一起发给 LLM 生成答案。

Q42 Embedding 是什么？

把文本转成一串数字（向量），让计算机能计算语义相似度。通俗理解：把每个词/句子映射到高维空间中的一个点，意思相近的点离得近。

项目应用：把用户兴趣和视频标题都转向量，然后做向量相似度检索，找语义相似的视频。

Q43 你怎么用 AI 辅助开发的？

1. 需求拆解：把大需求拆成小模块，写清楚技术方案

2. Prompt 驱动：给 AI 详细上下文（技术栈、接口定义、代码规范），让它生成代码

3. 代码审查：AI 生成的代码我会 review，检查逻辑和边界

大约 70% 核心代码自己写，30% AI 辅助。简历生成器项目就是典型产物。

Q44 视频内容理解 Agent 怎么实现的？

多模态管线——抽帧 + 视觉理解 + 音频提取 + 语音识别，最后用 LLM 融合生成摘要。

1. 帧提取：用 FFmpeg 按场景切换抽关键帧

2. 视觉理解：用通义千问视觉模型对帧做图片理解，生成画面描述

3. 音频提取 + 语音识别：提取音轨，用语音识别模型转文字（字幕）

4. 融合推理：把画面描述+字幕交给大语言模型，生成结构化视频摘要

容错设计：视觉模型或语音识别失败时不中断，LLM 根据已有信息降级生成摘要。异步处理，90秒超时。

Q45 智能推荐 Agent 怎么实现的？

- 微服务：提供推荐、向量化、摘要三个接口

Q47 余弦相似度是什么？怎么算？

通过计算两个向量的夹角余弦值来衡量相似度。

公式：cos = A·B / (|A| × |B|)。A·B 是点积，|A|、|B| 是向量的模。

取值范围 [-1, 1]，值越大越相似。

Q49 热度新鲜度排序怎么和向量结合？

1. 先通过向量相似度召回语义相关的候选视频

2. 对候选视频计算综合得分：向量相似度 × α + 热度分 × β + 新鲜度分 × γ

3. 按综合得分排序返回

Q59 PDF 导出怎么实现的？怎么保证单页 A4 不截断？

用 html2canvas 截图 + jsPDF 生成 PDF 的方案。

完整流程：

1. 定位预览元素，等待图片加载完成

2. 清除缩放变换，按原始 A4 尺寸渲染

3. 计算 A4 比例：截图高度 = 宽度 × (297/210)

4. html2canvas 截图（scale 1.5 倍）

5. jsPDF 创建 A4 页面，把截图铺满整页

6. 写入不可见文本层

7. 用 pdf-lib 的 EmbeddedFile 把完整简历 JSON 作为标准附件嵌入

怎么保证单页不截断：截图前固定高度为 A4 高度，溢出内容隐藏，截图宽高比 = A4 宽高比。

Q60 html2canvas 有什么坑？你怎么解决的？

坑 1：CSS 变量 var() 不渲染 - 在 onclone 回调中用 getComputedStyle 获取实际颜色值，内联设置到克隆元素上

坑 2：gradient 渐变渲染出错 - 检测到 gradient 就降级为纯色，提取第一个颜色值

坑 3：clip-path 不支持 - 直接移除 clip-path 属性

坑 4：flex 布局 align-items: stretch 不生效 - 显式设置侧边栏高度 = 容器高度

坑 5：预览缩放干扰截图 - 截图前临时清除 transform，截图后恢复

Q61 PDF 导入怎么做到无损恢复的？

实现了导出 → 导入双向无损，三级导入策略：

1. 第一级：EmbeddedFile 附件恢复（100% 精确） - 导出时用 pdf-lib 把简历 JSON 作为标准附件嵌入 PDF，导入时用 getAttachments() 读取

2. 第二级：不可见文本层提取 - 导出时写入了不可见的文本标记，如果附件丢失，从文本层提取

3. 第三级：OCR + 文本提取 - 如果以上都失败，用 PDF.js 提取文本，提取不到用 Tesseract.js OCR

Q64 自动保存怎么实现的？防抖具体怎么做？

自动保存机制：用 Vue 的 watch 深度监听简历数据变化 → 数据变化时触发防抖保存函数 → 防抖 500ms 后把数据序列化为 JSON 存入 localStorage

防抖具体实现：

1. 定义一个定时器变量 saveTimer

2. autoSave 函数被调用时，先清除已有的定时器

3. 设置新的定时器，500ms 后执行保存

4. 如果 500ms 内再次调用，清除上一个定时器，重新计时

5. 只有用户停止编辑 500ms 后才真正执行保存

为什么用防抖不用节流？ 用户编辑简历是离散事件（逐字输入），需要在用户停止输入后保存一次。防抖只在最后一次触发后执行，正好满足需求。

Q65 Vue 3 组合式 API 在项目里怎么用的？

Q75 Qt 信号槽的连接类型？

5种：

1. 自动连接（默认）：同线程直接调用，跨线程队列投递

2. 直接连接：同步直接调用，在发射信号的线程中执行

3. 队列连接：异步队列投递，在接收者线程的事件循环中执行

4. 阻塞队列连接：阻塞等待跨线程完成，不能在同线程用（会死锁）

5. 唯一连接：防止重复连接

项目应用：解码线程通过信号通知主线程更新 UI，用默认的自动连接，跨线程时自动走队列连接。

Q102 OOM要不要补货？

OOM（Out of Memory）是 Linux 内核在系统内存不足时的保护机制，触发 OOM Killer 杀死进程释放内存。

OOM 机制流程：内存回收 → 触发 OOM Killer → 根据 oom_score 分数选择"代价最小"的进程杀死

"补货"措施：vm.overcommit_memory=2 禁止过度分配、关键服务 systemd Restart=always、增加 swap、cgroups 限制最大内存

Q103 完美转发解决什么问题？

完美转发解决的是在函数模板中保持传入参数的左值/右值属性的问题。

核心问题：右值引用参数在函数内部会变成左值，导致本该触发移动构造却变成拷贝构造。

实现方式：通过 std::forward<T>(arg) + 引用折叠规则：

- 原参数是左值 → 转发后仍是左值

- 原参数是右值 → 转发后仍是右值

作用：保证移动语义正常生效，减少不必要拷贝，常用于工厂函数、emplace 接口、线程池任务包装。

Q108 大量TIME_WAIT的原因

TIME_WAIT 是 TCP 四次挥手后主动关闭方进入的状态，持续 2MSL。

原因：客户端大量主动关闭连接（HTTP 短连接）、服务端未开启端口复用、并发请求量巨大、程序未合理复用连接

解决方案：启用 Keep-Alive 长连接、使用连接池、开启端口复用、调整 tcp_tw_reuse=1

一、音视频 / 短视频项目相关

⭐⭐⭐⭐⭐ 音视频同步是怎么实现的

出现公司：海神医疗、CVTE技术面、剪映三面、多益网络、拼多多二面、拼多多客户端1面、拼多多一面、拓维信息、小红书PE（9家）

答：

我用的是以音频为主时钟的同步方案。选择音频做基准有三个原因：音频采样率固定，时间戳计算精确；人对声音卡顿比画面卡顿更敏感；音频不能变速播放（变速会变调），而视频可以丢帧或延迟来追赶。

具体逻辑：获取当前音频播放的时间戳作为主时钟，视频帧解码后对比视频时间戳和音频时间戳。视频比音频快了就丢掉这帧追赶；视频比音频慢了就延迟渲染等音频追上来；差不多就正常渲染。

⭐⭐⭐⭐⭐ 音视频同步为什么用视频追赶音频？音频追视频为什么不好？

出现公司：剪映三面、拼多多一面（3家）

答：

音频追视频不好的原因：第一，音频是连续的流，不能随便丢帧或变速，丢了会有明显的声音断裂，变速会变调；第二，音频采样率固定，时间戳精确，适合做基准；第三，视频帧可以丢、可以延迟、可以重复显示，人对画面微小卡顿容忍度高。所以让灵活的视频去追赶不可变的音频，是更合理的方案。

⭐⭐⭐⭐ 音画不同步的原因？播放流程是什么？

出现公司：拼多多客户端1面、拼多多二面、CVTE技术面（4家）

答：

不同步的原因：音视频解码速度不同、网络抖动导致包到达时间不同、CPU 负载高时解码慢、渲染管线延迟。

播放流程：打开文件 → 获取流信息 → 查找解码器 → 打开解码器 → 读包线程循环读取压缩包 → 视频包进视频队列、音频包进音频队列 → 视频解码线程从队列取包解码出帧 → YUV 转 RGB → 通过信号发给主线程 OpenGL 渲染 → 音频回调线程从队列取包解码 → 重采样 → 拷贝到 SDL 缓冲区播放。两个队列是生产者消费者模型，读包是生产者，解码是消费者。

⭐⭐⭐⭐ 以音频时钟同步时，画面会不会出现等待、卡顿或丢帧？

出现公司：海神医疗、剪映三面（3家）

答：

会的，这是正常的同步行为。视频比音频快了，就丢掉当前帧追赶，画面会跳一下但用户基本感知不到；视频比音频慢了，就延迟渲染等音频追上来，画面会轻微卡顿。只要差距在合理范围内（比如几十毫秒），用户基本感知不到。如果差距太大，说明解码性能或网络有问题，需要加缓冲队列平滑抖动。

⭐⭐⭐⭐ 丢帧万一丢的是 I 帧怎么办？

出现公司：拓维信息二面（2家）

答：

I 帧是关键帧，后面的 P 帧依赖它解码。如果丢了 I 帧，后面的 P 帧全部解码失败，画面会花屏，直到下一个 I 帧才能恢复。所以丢帧策略不能丢 I 帧。正确做法是：落后需要追赶时，只丢 P 帧，遇到 I 帧必须保留；如果落后太多，可以跳过一整个 GOP（I 帧到下一个 I 帧之间），直接从下一个 I 帧开始解码。

⭐⭐⭐⭐ FFmpeg 是以什么方式接入的？用的什么接口？

出现公司：海神医疗、河泊创新（3家）

答：

以库的形式集成到项目中，不是调命令行。用的 FFmpeg 4.2.2，32 位 MinGW 编译的预编译库。因为是纯 C 写的，C++ 项目引入时要用 extern "C" 包裹头文件。

主要流程：打开输入文件、获取流信息、查找解码器、打开解码器、循环读取压缩数据包、把压缩包解码成原始帧、视频帧做 YUV 转 RGB、音频帧做重采样。FFmpeg 用的是动态链接库。

⭐⭐⭐⭐ 解码后的视频画面怎么显示？渲染用的什么？

出现公司：海神医疗、小米二面（4家）

答：

解码出来的是 YUV 数据，不能直接显示，需要转成 RGB。我用的是 OpenGL 纹理映射渲染，不是 Qt 自带的组件。继承 Qt 的 OpenGL 控件，初始化时创建纹理对象，每收到一帧 RGB 数据就上传为 OpenGL 纹理，画一个全屏四边形把纹理贴上去，走 GPU 渲染。比 QPainter 的 CPU 渲染性能好很多。

⭐⭐⭐⭐ OpenGL 的渲染过程？可编程的部分有哪些？

出现公司：小米二面（2家）

答：

OpenGL 渲染管线大致分几步：顶点数据输入 → 顶点着色器（处理顶点坐标变换）→ 图元装配 → 光栅化（把图元转成像素）→ 片元着色器（计算每个像素的颜色）→ 测试与混合 → 帧缓冲。

可编程的部分是顶点着色器和片元着色器。顶点着色器负责顶点的位置变换，比如旋转、缩放、投影；片元着色器负责每个像素的颜色计算，比如纹理采样、光照计算。

如果用 OpenGL 做表情包处理之类的图像处理，主要在片元着色器里做——对每个像素的颜色做变换，比如灰度化、反色、模糊、边缘检测。我没做过 GLSL 编程，只用了固定管线做纹理映射。

⭐⭐⭐ SDL 和 OpenGL 在播放模块中分别负责什么？有直接关系吗？

出现公司：海神医疗（2家）

答：

SDL 负责音频输出和线程管理，OpenGL 负责视频画面渲染。两者没有直接关系——SDL 不管视频渲染，OpenGL 不管音频。我在项目里用 SDL 的音频设备接口播放声音，用 SDL 创建独立线程跑视频解码，用 OpenGL 把解码后的 RGB 数据渲染到屏幕上。两者通过共享的数据包队列间接联系：SDL 音频回调从队列取音频包，OpenGL 渲染从队列取视频包。

⭐⭐⭐⭐ 断点续传怎么实现的？

出现公司：百度二面、拼多多二面、小米一面、拼多多客户端1面、上海凌瓤（6家）

答：

文件分块上传，每块有唯一编号。服务端维护一张上传任务表，记录每个文件已收到哪些块。上传中断后重连，客户端先查询已上传的块列表，跳过已上传的，只传缺失的。全部块上传完成后，服务端按顺序合并成完整文件，再做一次 MD5 校验确认完整性。

如果客户端上传了块但服务端的成功响应丢了，客户端重发，服务端通过块编号去重，不会重复写入。

断点续传除了用 SQLite 本地存储，还可以用 Redis 存上传进度，或者用文件记录（每个块上传完写一个 .done 标记文件）。

⭐⭐⭐⭐ 多线程上传怎么做？数据不连续怎么办？

出现公司：拼多多二面、拼多多客户端1面（3家）

答：

多线程上传就是把文件分成多个块，多个线程并行上传不同的块。比单线程快是因为网络 IO 有延迟，多线程可以重叠多个块的传输时间，充分利用带宽。

数据不连续的问题：多个线程到达顺序不确定，但每块有编号，服务端按编号拼装，不依赖到达顺序。如果某块传输失败，只需要重传那一块，不影响其他块。多线程断点续传就是记录每个块的上传状态，断线后只补传未完成的块。

⭐⭐⭐⭐ 秒传和断点续传的过程？为什么用 MD5？

出现公司：百度三面、小红书PE、拼多多（4家）

答：

秒传：上传前先算文件的 MD5 哈希值，发给服务端查询。如果服务端已存在相同 MD5 的文件，说明这个文件之前有人传过，直接在数据库里创建一条引用记录，不需要再传文件本身。

断点续传：文件分块，每块算 MD5，上传前先查询哪些块已存在，只传缺失的块。

用 MD5 的原因：MD5 计算快，输出固定 128 位，碰撞概率极低（约 2 的负 128 次方），足够区分不同文件。更严格的话可以用 SHA-256，碰撞概率更低，但计算稍慢。

⭐⭐⭐⭐ 文件上传怎么保证完整性和一致性？

出现公司：百度二面、小红书PE（4家）

答：

三层保障：第一，每块上传时带 CRC 校验，服务端收到后校验，不匹配就要求重传；第二，全部块合并后算整个文件的 MD5，跟客户端上传的 MD5 对比；第三，如果用 TCP 协议本身保证有序不丢，加上应用层校验就够。如果上传发现文件内容不一致，以服务端为准，客户端重新上传有问题的块。

⭐⭐⭐⭐ 从摄像头采集到渲染之间，像素格式怎么转换？为什么？

出现公司：剪映二面、金绿汇成（3家）

答：

摄像头原生输出通常是 YUYV 或 MJPEG 格式。YUYV 是 YUV422 打包格式。处理流程：先转成 YUV420P（编码常用格式），如果需要显示就再转成 RGB。

为什么要转：编码器（H.264）要求 YUV420P 输入；显示器和 OpenGL 需要 RGB 格式；YUV420P 比 RGB 数据量小一半（UV 通道降采样），传输和存储更省。

⭐⭐⭐ YUV 和 RGB 的区别？YUV 采样怎么做？

出现公司：小红书PE、剪映二面（3家）

答：

RGB 是红绿蓝三通道，每像素 3 字节。YUV 是亮度（Y）加色度（U/V）分离，人眼对亮度比对色度敏感，所以 UV 可以降采样。YUV420 中 U 和 V 的采样率只有 Y 的 1/4，数据量是 RGB 的一半。

采样方式：4:4:4（不降采样）、4:2:2（水平减半）、4:2:0（水平和垂直都减半，最常用）。视频编码普遍用 YUV420P，显示时转 RGB。

⭐⭐⭐ I 帧和 P 帧的区别？

出现公司：小红书PE、拓维信息（3家）

答：

I 帧（关键帧）完整编码，不依赖其他帧，可独立解码。P 帧（预测帧）只编码跟前一帧的差异，依赖前面的帧。视频流定期插 I 帧，第一个必须是 I 帧。丢 I 帧后面 P 帧全废，花屏到下一个 I 帧才恢复。

⭐⭐⭐ H.264 和 H.265 的区别？H.265 怎么实现更高压缩比？

出现公司：河泊创新（2家）

答：

H.265（HEVC）比 H.264 压缩率高约 50%，同等画质下码率减半。实现方式：H.264 用 16x16 宏块，H.265 用 8x8 到 64x64 可变大小的编码单元（CTU），大块平坦区域用大块编码减少开销；更多预测方向（H.264 最多 8 个方向，H.265 有 35 个）；更精细的变换和量化。代价是编码复杂度大幅增加。

⭐⭐⭐ jitter buffer 是什么？阈值为什么 5-15 帧？可以动态浮动吗？

出现公司：剪映三面（2家）

答：

Jitter buffer 是接收端缓冲区，平滑网络抖动。包到达时间不一致，直接解码会卡顿，先缓存一定帧数再按时间戳顺序送解码器。

5-15 帧是经验值：太小缓冲不够还是卡，太大延迟高（15 帧 ≈ 250ms-500ms）。可以动态浮动——网络好时减小阈值降低延迟，网络差时增大阈值防卡顿。根据丢包率和抖动统计自适应调整。

⭐⭐⭐ FLV 格式怎么做流式播放？

出现公司：剪映三面（2家）

答：

FLV 由 Header 和 Body 组成，Body 是一系列 Tag（视频/音频/脚本），每个 Tag 前有 4 字节的 Previous Tag Size。流式播放就是服务器持续发送 Tag，客户端边收边解析边播放，不需要等整个文件下载完。FLV 结构简单、Tag 之间独立，适合流媒体。RTMP 协议底层传输的就是 FLV Tag。

⭐⭐⭐ 上传视频为什么用二进制分片而不是 HTTP？

出现公司：小红书PE（2家）

答：

二进制分片更灵活：可以自定义协议头、断点续传、多线程并行上传、精确控制每块大小和重传策略。HTTP 分片上传也可以（Content-Range），但 HTTP 头开销大，每块都有完整的 HTTP 头；而且 HTTP 是文本协议，传二进制数据需要编码，效率低。二进制协议开销小、更高效。缺点是不可读、调试麻烦、需要自定义协议设计。

⭐⭐⭐ 静音检测怎么检测？音频采集为什么改用 Opus？

出现公司：拓维信息一面（2家）

答：

静音检测：计算每帧音频的能量（RMS）和过零率，低于阈值判定为静音，丢弃不编码不传输，节省带宽。

Opus 比 AAC/MP3 优势：低延迟（最低 2.5ms 帧）、码率范围广（6kbps-510kbps）、音质好、特别适合实时通信。AAC 适合流媒体点播，Opus 适合实时通话。

⭐⭐⭐ 音频重采样是什么？

出现公司：拓维信息一面（2家）

答：

重采样就是改变音频的采样率、声道数或采样格式。比如源音频是 48kHz 双声道 16bit，但 SDL 音频设备只支持 44.1kHz 单声道，就需要重采样。FFmpeg 的 swr_convert 就是做这个的。原理是插值或抽取——上采样用插值补点，下采样用抽取去点，还要加低通滤波器防止混叠。

⭐⭐⭐ 如果音视频有音频输出，同时再播放音乐，双声源怎么处理？

出现公司：多益网络（1家）

答：

两种方案：一是音频混音，把两路音频的采样数据按比例叠加（注意溢出，用饱和截断或归一化），合成一路输出；二是分别打开两个音频设备，让系统混音。实际项目里一般是混音后输出，更可控。SDL 可以打开多个音频设备，或者用一个回调函数里混音。

⭐⭐⭐ 摄像头采集格式？OpenCV 原生输出什么？

出现公司：金绿汇成、河泊创新（3家）

答：

OpenCV 采集摄像头原生输出通常是 YUYV 或 MJPEG 格式。YUYV 是 YUV422 打包格式，每像素 2 字节。分辨率可能是 480P/720P/1080P，取决于摄像头硬件。码流格式需要主动管控——通知摄像头输出 H.264 还是不压缩的原始流。OpenCV 简单但工程短板是延迟不可控、格式支持有限，量产落地需要关注延迟、码流格式、分辨率适配。

⭐⭐⭐ 如果给你一个机器人，让你实现将视觉模块捕捉的视频投放到终端，你会怎么做？

出现公司：青心意创HR（1家）

答：

我会分几步：第一，视觉模块采集视频帧（用 OpenCV 或 GStreamer）；第二，把帧编码成 H.264 压缩流减少带宽；第三，通过网络（TCP/UDP/WebRTC）传到终端；第四，终端解码渲染。如果延迟要求高用 UDP + WebRTC，如果要求可靠用 TCP。考虑到机器人场景，可能网络不稳定，需要加丢包重传或 FEC 前向纠错。

⭐⭐⭐ 场景题：根据网络情况自动选择合适分辨率怎么设计？

出现公司：剪映三面（1家）

答：

设计自适应码率方案（ABR）。客户端实时监测带宽估计（根据下载速率算）、RTT、丢包率。根据指标分好/中/差三档，对应高/中/低清晰度。网络变差时降一档观察，不一次降到底；网络恢复时延迟 3-5 秒再升档，避免频繁切换。服务端提前转码好多个版本（1080P/720P/480P），客户端通过 HLS 或 DASH 协议无缝切换。

⭐⭐⭐ GPU 除了渲染还能干啥？在大模型领域呢？

出现公司：拼多多三面（1家）

答：

GPU 除了渲染还能做视频解码（硬解 DXVA2/NVDEC）、通用计算（CUDA/OpenCL）、科学计算、图像处理。在大模型领域，GPU 是训练和推理的核心硬件——因为大模型推理本质是大量矩阵乘法，GPU 的并行计算架构（成千上万个核心）特别适合这种密集计算，比 CPU 快几个数量级。

⭐⭐ 代码题：设计并实现视频导出流程的状态机

答：

⭐⭐⭐ 推流逻辑怎么实现？如何解决卡顿？

出现公司：字节二面（1家） 答： 推流就是客户端采集音视频 → 编码 → 按协议（RTMP/RTC）打包 → 发送到服务器。卡顿原因：网络带宽不够、编码太慢、采集帧率低。解决：自适应码率，网络差时降码率降分辨率；加发送缓冲区平滑抖动；丢帧策略，优先丢视频帧保音频；用 UDP 替代 TCP 减少重传延迟。

⭐⭐⭐ RTMP 的延迟表现如何？做过实际测试吗？

出现公司：海神医疗（2家） 答： RTMP 基于 TCP，延迟通常在 1-3 秒左右。延迟来源：TCP 三次握手 + 编码缓冲 + 发送缓冲 + 服务端缓冲 + 客户端缓冲。实测时我用 OBS 推流到服务器，客户端拉流播放，用手机秒表对比真实画面和播放画面，延迟大概 2 秒左右。对实时通信来说不够，但对直播场景可以接受。如果要更低延迟，可以用 WebRTC（基于 UDP，延迟可降到 500ms 以内）或 SRT 协议。

⭐⭐⭐ 如果让你加美颜和磨皮功能，你会加在哪里？

出现公司：剪映一面、剪映二面（3家） 答： 加在解码后、渲染前。流程：解码出 YUV 帧 → 转 RGB → 美颜处理（磨皮、美白、瘦脸）→ 渲染到屏幕。磨皮算法：先做肤色检测（YCrCb 空间判断肤色区域），然后对肤色区域做双边滤波——保边平滑，去掉痘印和细纹但保留五官轮廓。也可以加在渲染阶段——用 OpenGL 片元着色器做实时美颜，GPU 处理性能好，每像素做滤波计算。加在渲染之前的好处是可以用 CPU 预处理，加在着色器里的好处是 GPU 加载快。实际产品里一般用 GPU 着色器做，性能更好。

⭐⭐⭐ 做过缓冲机制吗？

出现公司：拼多多客户端1面（1家） 答： 做过。音视频播放有缓冲队列——读包线程把解码后的包放进队列，渲染线程从队列取包播放。队列大小一般缓存 1-2 秒的数据。队列太大延迟高，太小容易卡顿。网络播放时还有预缓冲——开始播放前先缓冲一定数据再开始渲染，避免一开始就卡。缓冲策略：队列低于阈值时暂停渲染等待数据，高于阈值时正常播放。在线视频还可以做二级缓冲——内存缓冲 + 磁盘缓冲，内存缓冲满了写磁盘，Seek 时先查磁盘缓存。

⭐⭐⭐ 采集到原始视频流后，存储、拆帧、逐帧处理流程？

出现公司：河泊创新（1家） 答： 采集到原始视频流（YUV/RGB）后：如果只是显示，直接转 RGB 交 OpenGL 渲染。如果要存储，先转 YUV420P 再用 H.264 编码压缩，封装成 MP4 或 FLV 写文件。拆帧就是按帧率从视频流里取单帧图像——FFmpeg 里循环 av_read_frame 读包，avcodec_send_packet + avcodec_receive_frame 解码出单帧。逐帧处理：对每一帧做图像处理（美颜、目标检测等），处理完再编码写回或直接渲染。

⭐⭐⭐ 视频编码格式有哪些？FFI 是什么？

出现公司：河泊创新（1家） 答： 常见视频编码格式：H.264（最普及，兼容性好）、H.265/HEVC（压缩率更高但编码复杂）、VP8/VP9（Google 开源）、AV1（新一代开源编码，压缩率最高但编码慢）。音频编码：AAC（最常用）、Opus（低延迟适合实时通信）、MP3（老旧但兼容好）。 FFI（Foreign Function Interface）是外部函数接口，让一种语言调用另一种语言写的代码。比如 Python 通过 FFI 调用 C 写的 FFmpeg 库，或者 Rust 通过 FFI 调用 C 库。在音视频项目里，如果用 Python 做上层逻辑但需要调 FFmpeg 的 C 接口，就通过 FFI 桥接。

⭐⭐⭐ 自定义二进制协议是什么？业务包部分数据怎么处理？包头内容？

出现公司：小红书PE（3家） 答： 我项目里自定义了二进制协议做文件上传。包头包含：魔数（标识协议）、消息类型（上传/下载/心跳等）、包体长度、分块编号、文件 ID。包头固定长度，接收端先读包头解析出包体长度，再读对应长度的包体。 业务包只收到部分数据（TCP 粘包/拆包）：接收端维护一个缓冲区，收到数据先追加到缓冲区，然后循环解析——只要缓冲区里有完整包头就解析包头，根据包头里的包体长度判断是否收齐了整个包，收齐了就处理并从缓冲区移除，没收齐就等下次数据到达再继续。就是"先读包头长度 → 再按长度读包体 → 不足就等"的循环。

⭐⭐⭐ FFmpeg 后期怎么优化？

出现公司：竞业达（1家） 答： 几个方向：一是硬件解码，用 DXVA2（Windows）或 VAAPI（Linux）做硬解，GPU 解码比 CPU 快好几倍，CPU 占用大幅下降。二是多线程解码，H.264 帧之间有依赖但 GOP 内的 B 帧可以并行解码。三是零拷贝优化，解码出的 YUV 数据直接传给 OpenGL 纹理，不做 CPU 拷贝。四是码率优化，根据网络状况动态调整编码码率。五是内存池，避免频繁 malloc/free 解码缓冲区。

⭐⭐ 为什么上传时用 4K 分块？

出现公司：百度三面（1家） 答： 4K（其实是 4MB）是经验值。太小（如 64KB）：块数太多，每块都有协议头开销，网络请求次数多，效率低。太大（如 64MB）：一块传失败要重传整个大块，浪费带宽；内存占用大，多线程上传时每个线程都要缓冲一个块。4MB 在大多数网络条件下比较平衡——单块传输时间可控，失败重传成本不高，协议头开销占比小。实际可以根据网络状况动态调整：好网络用大块（8MB），差网络用小块（1MB）。

⭐⭐⭐⭐ FFmpeg 组件架构？各库的职责划分？

出现公司：海神医疗、河泊创新、PDF面经总结（4家） 答： FFmpeg 主要由几个库组成：libavformat 负责容器格式的封装和解封装（MP4、FLV、TS），处理流的读写；libavcodec 负责编码和解码（H.264、AAC）；libswscale 负责图像缩放和颜色空间转换（YUV→RGB）；libswresample 负责音频重采样（采样率、声道转换）；libavfilter 负责滤镜处理（裁剪、水印、调色）；libavutil 是工具库（内存、日志、数学运算）。 我项目主要用了 libavformat 做解复用、libavcodec 做解码、libswscale 做 YUV 转 RGB、libswresample 做音频重采样。ffprobe 工具可以用来查看媒体文件信息，ffmpeg 工具可以做转码、剪切等操作。

⭐⭐⭐⭐ 容器格式和编码格式的区别？常见格式有哪些？

出现公司：海神医疗、PDF面经总结（3家） 答： 容器格式是装音视频数据的"箱子"，编码格式是数据压缩的"算法"。一个容器里可以装不同编码的音视频流。 常见容器：MP4（最通用，支持流式和本地）、FLV（直播常用，低延迟）、TS（流媒体，抗丢包）、MKV（开源，支持多音轨多字幕）、WebM（Google 推，VP8/VP9）。 常见视频编码：H.264/AVC（最普及，兼容性好）、H.265/HEVC（压缩率比 H.264 高 50%）、VP9（Google 开源）、AV1（新一代开源，压缩率更高）。常见音频编码：AAC（主流，音质好）、MP3（老牌）、Opus（低延迟，实时通信首选）。 我项目播放器支持 MP4 和 FLV，上传视频统一存为 MP4 容器 + H.264 编码 + AAC 音频。

⭐⭐⭐⭐ pts/dts/timebase/帧率是什么？有什么坑？

出现公司：剪映、PDF面经总结（3家） 答： pts（Presentation Timestamp）是显示时间戳，决定画面什么时候显示给用户；dts（Decoding Timestamp）是解码时间戳，决定帧什么时候送入解码器。因为有 B 帧的存在（B 帧需要参考前后帧），解码顺序和显示顺序不一样，所以 pts 和 dts 可能不同。timebase 是时间基，时间戳的实际值 = pts × timebase。 帧率是每秒显示多少帧（fps），常见的 24、30、60。坑：1）B 帧导致 dts 和 pts 顺序不同，解码时要按 dts 排序，显示时按 pts 排序；2）timebase 不同导致时间戳计算错误，不同容器 timebase 可能不同（MP4 用 1/90000，FLV 用 1/1000）；3）变帧率视频（vfr）pts 不均匀，不能简单用帧率计算时间。

⭐⭐⭐⭐ 软解码和硬解码的区别？各自适用场景？

出现公司：海神医疗、小米、PDF面经总结（4家） 答： 软解码：纯 CPU 计算，兼容性好但 CPU 占用高、功耗大、可能发热降频。 硬解码：用 GPU 或专用硬件解码芯片（DXVA2/VAAPI/NVDEC/MediaCodec/VideoToolbox），CPU 占用低、功耗低、性能好，但兼容性差，不同平台 API 不同。 我项目用的是 DXVA2 硬件解码（Windows 平台），配合自动降级策略——先尝试硬解，失败就回退到软解。选择 DXVA2 是因为 Windows 原生支持，不需要额外安装显卡驱动 SDK。硬解和软解的输出格式不同：硬解通常输出 NV12，软解通常输出 YUV420P，渲染前都要转 RGB。

⭐⭐⭐ 码率控制：CBR/VBR/CRF 的区别？

出现公司：PDF面经总结（2家） 答： CBR（Constant Bit Rate）恒定码率：整个视频码率固定，每秒数据量一样。优点是文件大小可预测，适合直播；缺点是复杂场景画质下降。 VBR（Variable Bit Rate）可变码率：码率随场景复杂度变化，简单场景低码率，复杂场景高码率。优点是画质稳定；缺点是文件大小不可预测。 CRF（Constant Rate Factor）恒定质量：指定一个质量因子（0-51，越小越好），编码器自动调整码率保持质量恒定。18-28 是常用范围，23 是默认。优点是一键获得质量与大小的平衡；缺点是无法控制文件大小。 我项目上传视频时用 CRF 28 做转码，在画质和体积间取得平衡。

⭐⭐⭐ FFmpeg 推流/拉流：RTMP/HTTP-FLV/HLS/DASH 的差异？

出现公司：剪映、PDF面经总结（3家） 答： RTMP：基于 TCP，延迟 1-3 秒，Adobe 开发，直播推流最常用。缺点是 TCP 队头阻塞，弱网下延迟增大。 HTTP-FLV：把 FLV 流封装在 HTTP 响应里，延迟 1-3 秒，穿防火墙好，CDN 友好。相比 RTMP 更适合播放端。 HLS：基于 HTTP，把视频切成小段 ts 文件，客户端按顺序下载播放。延迟 5-30 秒（取决于切片长度），但兼容性最好（iOS 原生支持），适合点播和延迟不敏感的直播。 DASH：类似 HLS 但基于 MPEG-DASH 标准，支持自适应码率（ABR），更灵活。 延迟排序：RTMP ≈ HTTP-FLV < HLS < DASH。我项目用的是 RTMP 推流 + HTTP Progressive 拉流（8081 端口）。

⭐⭐⭐ FFmpeg 滤镜系统（libavfilter）？

出现公司：PDF面经总结（1家） 答： libavfilter 是 FFmpeg 的滤镜处理库，用 filter graph 描述滤镜链。基本概念：滤镜（filter）做单一处理（如 scale 缩放、overlay 叠加、crop 裁剪），滤镜链（filterchain）是多个滤镜串联，滤镜图（filtergraph）是多个链并联。 常用滤镜：scale=640:480（缩放）、crop=w:h:x:y（裁剪）、overlay=x:y（叠加水印/画中画）、concat（拼接）、fps=30（改帧率）、hue（调色调）、drawtext（加文字）。 画中画实现：两个输入流，主画面和子画面，用 overlay 滤镜把子画面叠加到主画面的指定位置。多路混流类似，用 concat 或 overlay 组合。 我项目没用 libavfilter，美颜磨皮如果要做可以加在 OpenGL 片元着色器里，比 FFmpeg 滤镜性能更好（GPU 加速）。

⭐⭐⭐ 直播/点播中延时、卡顿、花屏、音画不同步的常见原因及调优？

出现公司：剪映、PDF面经总结（3家） 答： 延时原因：编码缓冲（GOP 太大）、网络传输延迟、播放端缓冲区太大。调优：减小 GOP、用低延迟协议（RTMP/WebRTC）、减小播放缓冲。 卡顿原因：网络带宽不足、解码性能不够、缓冲区太小。调优：自适应码率（ABR）、增大缓冲区、启用硬件解码。 花屏原因：丢帧丢了 I 帧、解码错误、传输数据损坏。调优：不丢 I 帧、加错误校验、丢包重传。 音画不同步原因：时钟基准不一致、解码延迟不同、网络抖动。调优：统一时钟基准（音频主时钟）、加 jitter buffer 平滑抖动。

⭐⭐⭐ FFmpeg 跨平台编译常见问题？

出现公司：PDF面经总结（1家） 答： 常见问题：1）依赖库缺失——x264/x265/fdk-aac 需要单独编译，license 要注意（x264 是 GPL，fdk-aac 是非商业）。2）交叉编译——Android 需要 NDK 工具链，iOS 需要指定 sysroot。3）32/64 位匹配——我项目用 32 位 MinGW 编译，FFmpeg 库也要 32 位的。4）动态/静态链接——静态库编译要加 --enable-static --disable-shared。5）license 合规——LPL vs GPL，商业用要避免 GPL 组件。 我项目直接用预编译的 FFmpeg 4.2.2 32 位库，没有自己编译，省去了交叉编译的麻烦。配置时用 --enable-decoder=h264 --enable-parser=h264 确保需要的解码器启用。

⭐⭐⭐⭐ Qt 信号/槽机制底层原理？几种连接类型？

出现公司：CVTE、PDF面经总结（5家） 答： 信号/槽底层原理：Qt 用 moc（Meta-Object Compiler）在预处理阶段生成额外的 C++ 代码，包含信号/槽的元信息。emit 信号时，Qt 根据连接类型决定调用方式——直接调用槽函数（DirectCall）或通过事件队列投递（QueuedCall）。 四种连接类型： - Qt::DirectConnection：信号发出时立即在发送者线程执行槽函数（同步调用）。 - Qt::QueuedConnection：信号发出时把调用封装成事件投递到接收者线程的事件队列，接收者线程的事件循环取出后执行（异步调用）。 - Qt::BlockingQueuedConnection：类似 Queued 但发送者阻塞等待槽函数执行完（不能同线程用，会死锁）。 - Qt::AutoConnection（默认）：同线程自动用 Direct，跨线程自动用 Queued。 我项目里视频解码线程通过信号把帧数据发给主线程渲染，用的就是 AutoConnection——跨线程时自动走 Queued，安全且不需要手动加锁。

⭐⭐⭐⭐ Qt 事件循环工作流程？事件如何分发？

出现公司：CVTE、PDF面经总结（4家） 答： Qt 事件循环（QEventLoop/QCoreApplication::exec）：内部是一个 while 循环，不断从事件队列取事件 → 调用 QCoreApplication::notify() → 发送到目标对象的 event() 方法 → event() 根据事件类型分发给对应的 *Event() 处理函数（如 mousePressEvent、keyPressEvent、paintEvent）。 事件来源：系统消息（鼠标键盘）、定时器（QTimer）、网络（QSocketNotifier）、自定义事件（postEvent/sendEvent）、信号/槽的 QueuedConnection。 事件过滤器（eventFilter）：在事件到达目标对象之前拦截，可以做全局拦截。安装：obj->installEventFilter(filterObj)，在 filterObj 的 eventFilter() 里处理。 我项目用事件过滤器实现了视频卡片的全局右键菜单拦截。

⭐⭐⭐⭐ Qt 父子对象树内存管理？避免野指针？

出现公司：CVTE、PDF面经总结（3家） 答： Qt 的内存管理基于父子对象树：给 QObject 设置 parent 后，parent 析构时会自动 delete 所有 children。所以通常只需要 delete 顶层对象，子对象自动释放。 注意事项：1）不能 delete 一个还在被 parent 引用的子对象——应该用 deleteLater() 让事件循环安全删除。2）两个 parent 同级对象不能互相设为 parent，会循环引用。3）widget 设置了 parent 后，关闭窗口不会自动 delete，除非设了 Qt::WA_DeleteOnClose。4）栈上创建的 QObject 设了 parent，parent 析构时再 delete 会 double free——栈对象不要设 parent。 避免野指针：用 QPointer<T>（弱指针，对象删除后自动置 nullptr），或用 deleteLater() 替代直接 delete。

⭐⭐⭐ QThread 正确使用方式？继承 QThread vs moveToThread？

出现公司：CVTE、PDF面经总结（4家） 答： 两种方式： 1. 继承 QThread 重写 run()：在 run() 里执行耗时逻辑。简单直接，但槽函数仍在主线程执行（除非手动切换）。 2. Worker 对象 + moveToThread：创建 Worker 类继承 QObject，实例化后 moveToThread 到 QThread，通过信号/槽触发工作函数。所有槽函数都在新线程执行。 推荐用第二种（moveToThread），因为：更灵活（一个线程可以跑多个 worker）、更安全（槽函数自动在新线程执行）、更好管理（信号/槽驱动，不需要手动控制 run 循环）。 我项目里视频解码用的是第一种（继承 QThread 重写 run），因为解码是一个持续循环不需要响应外部信号。如果需要响应外部命令（如暂停、停止），moveToThread 更合适。

⭐⭐⭐⭐ 跨线程信号槽如何保证线程安全？

出现公司：CVTE、PDF面经总结（3家） 答： 跨线程信号/槽用 Qt::QueuedConnection（AutoConnection 在跨线程时自动选择）。原理：emit 信号时，Qt 把参数拷贝一份，封装成 QMetaCallEvent 事件，投递到接收者线程的事件队列。接收者线程的事件循环取出事件后执行槽函数。因为参数是拷贝的，且槽函数在接收者线程执行，所以天然线程安全——不需要手动加锁。 注意事项：1）参数必须是 Qt 能识别的元类型（注册过的类型），自定义类型要 qRegisterMetaType<MyType>()。2）引用传递跨线程会被拷贝（不是真正的引用）。3）频繁跨线程传递大数据（如视频帧）要注意拷贝开销，可以用指针 + 智能指针管理生命周期。 我项目里解码线程把 YUV 帧数据通过信号发给主线程，参数用的是自定义的 FrameData 结构（注册了 Q_DECLARE_METATYPE），主线程收到后转 RGB 渲染。

⭐⭐⭐ Qt Model/View 框架？关键接口？

出现公司：PDF面经总结（2家） 答： Qt Model/View 架构：Model 管理数据，View 负责显示，Delegate 负责编辑。三者分离，数据变化时 Model 发信号通知 View 更新。 QAbstractItemModel 关键接口： - rowCount()/columnCount()：返回行列数。 - data(index, role)：返回指定位置的数据（DisplayRole 显示文本、DecorationRole 图标、EditRole 编辑值等）。 - setData(index, value, role)：修改数据。 - flags(index)：返回项目标志（可编辑、可选、启用等）。 - insertRows()/removeRows()：增删行。 关键信号：dataChanged()（数据变化）、beginInsertRows()/endInsertRows()（增行前后必须调用，否则 View 不更新）。 我项目用 QStringListModel 做搜索补全、QSqlQueryModel 做数据库查询展示。视频列表用的是自定义 QAbstractListModel。

⭐⭐⭐ 视频分块上传如何实现断点续传与校验？

出现公司：字节跳动、PDF面经总结（3家） 答： 分块上传流程：1）前端计算整个文件的 MD5 作为唯一标识。2）按固定大小（如 4MB）切分成多个块，每块也算 MD5。3）上传前先请求服务端查询已上传的块（传文件 MD5），服务端返回缺失的块列表。4）只上传缺失的块，实现断点续传。5）所有块上传完后，服务端按顺序合并，计算合并后文件的 MD5 与前端传的 MD5 比对，一致则上传成功。 校验：文件级 MD5 校验完整性，块级 MD5 校验单块正确性。服务端顺序存储，合并时按块序号拼接。 大文件优化：多线程并发上传不同块（我项目用 3-4 个线程），失败块自动重试 3 次。秒传：文件 MD5 命中服务端已有记录，直接返回成功不上传。 --- ## 二、AI 相关项目问题

⭐⭐⭐⭐⭐ AI 辅助开发的流程是怎样的？

出现公司：小红书、CVTE、网易雷火、拼多多、剪映、影笑、字节、经纬恒润、识光科技（12+家） 答： 我的流程：先自己想好要做什么功能、怎么设计数据结构、交互流程是什么，然后写一个比较详细的提示词给 AI 工具（我用字节的 Trae），让 AI 生成代码框架。生成之后自己审查逻辑对不对、能不能跑通，不对的地方自己改或者让 AI 重新生成。 关键是我会拆需求——把大功能拆成小模块，每个模块单独让 AI 生成。这样每个模块代码量不大，审查起来快。开发过程中还会用 AI 排查报错，把错误信息贴给它让它分析原因。

⭐⭐⭐⭐⭐ Agent 和 LLM 的区别？

出现公司：河泊创新、小红书PE、河南兴序元、小米安卓一面（5家） 答： LLM 是大语言模型，本质是文本生成模型——给输入文本，输出文本，不能执行动作、不能联网、不能读写文件。 Agent 是以 LLM 为大脑的智能体，除了 LLM 做推理，还配了工具调用能力（搜索、代码执行、文件读写）、记忆系统（短期记忆和长期记忆）、规划能力（把任务拆解成步骤）。LLM 是被动的——你问它答；Agent 是主动的——给它一个目标，它自己规划步骤、调用工具、逐步完成。 简单说：LLM 是脑子，Agent 是有手有脚有记忆的完整的人。

⭐⭐⭐⭐⭐ 怎么知道 AI 生成的方案合不合理？怎么验证？

出现公司：小红书AI全栈、CVTE一面、百度二面、影笑HR、剪映HR、小红书PE（7家） 答： 第一，不让 AI 生成完直接用，一定自己审查逻辑，特别关注边界条件和异常处理。第二，对 AI 生成的代码跑测试，看结果对不对。第三，提示词里加约束——明确用什么框架、什么版本、什么设计模式，减少 AI 自由发挥。第四，遇到问题定位到具体哪一行，把错误信息反馈给 AI 让它改，而不是重新生成整个文件。 AI 会有幻觉——就是生成看起来合理但实际错误的内容。原因是大模型本质是概率预测下一个词，不是真正理解逻辑。应对方法就是审查 + 测试 + 约束。

⭐⭐⭐⭐ 上下文管理怎么做？怎么避免遗忘和溢出？

出现公司：小红书AI全栈、河泊创新、剪映二面、剪映一面（6家） 答： 大模型有上下文窗口限制，超出就记不住前面的内容。我的做法： 一是会话隔离——不同任务用不同的会话，避免无关上下文干扰。二是上下文压缩——长对话中定期让 AI 自己做摘要，把前面的关键信息压缩成简短描述。三是外部记忆——把关键信息写成文档，新会话开始时把文档喂给 AI。四是引用传递——把上一次的输出作为下一次的输入。 如果出现遗忘历史上下文，解决办法是：把关键决策和约定写在提示词模板里，每次对话都带上；或者用向量数据库做长期记忆，需要时检索相关内容注入上下文。

⭐⭐⭐⭐ Skill 和 MCP 是什么？有自己实现过吗？

出现公司：多益网络、剪映一面、影笑二面、小米安卓一面（5家） 答： MCP（Model Context Protocol）是标准协议，规定了 AI 工具怎么跟外部工具和数据源连接。相当于给 AI 装"插件"的统一接口标准。 Skill 是预定义的指令模板，告诉 AI 在特定场景下怎么做。比如"当代码报错时，先读错误日志，再定位文件，然后分析原因，最后给修复方案"。下次遇到代码报错，AI 就按这个流程走。 哪些适合放脚本：固定流程、不需要 AI 判断的重复操作。哪些适合放 Skill：需要 AI 理解上下文、做判断但有固定套路的任务。判断标准是——如果完全不需要 AI 的理解能力，就是脚本；如果需要 AI 理解但流程有套路，就是 Skill。 我自己写过 Skill，比如简历生成器里定义了"如何从 PDF 提取文本并匹配到简历数据结构"的 Skill。

⭐⭐⭐⭐ 多 Agent 怎么并行开发？怎么拆分任务？

出现公司：剪映二面、剪映一面、小米安卓一面（4家） 答： 把大任务拆成多个独立子任务，每个子任务交给一个子 Agent 处理，主 Agent 负责协调和汇总。拆分原则：子任务之间尽量低耦合，不要修改同一个文件。如果两个任务涉及同一个模块，就串行执行——一个改完了另一个再开始，避免冲突。 如果主 Agent 用好模型、子 Agent 用差模型，可能出现的问题是：主 Agent 的指令子 Agent 理解不了，或者子 Agent 生成的代码质量不够。解决方法是在指令里加更多约束和上下文，或者对子 Agent 的产出做额外审查。 多 Agent 之间通信：一般通过共享文件或消息传递，主 Agent 把任务描述写到文件里，子 Agent 读取后执行，完成后把结果写到另一个文件里。

⭐⭐⭐⭐ 提示词怎么写？怎么约束 AI 输出？

出现公司：网易雷火、CVTE技术面、中诺、小红书AI全栈（5家） 答： 我的提示词原则：第一，明确角色——"你是一个 C++ 开发工程师"。第二，描述背景——技术栈、框架版本、已有代码结构。第三，明确需求——要实现什么功能，输入输出是什么。第四，加约束——用什么设计模式、命名规范、代码风格，不要用什么。第五，给示例——需要特定格式就给个例子。第六，分步骤——复杂任务拆成多步。 约束 AI 输出的方法：在提示词里明确说"只输出代码不要解释"、"用 C++11 标准"、"不要用第三方库"、"函数命名用驼峰"。还可以用 JSON schema 约束输出格式。

⭐⭐⭐⭐ AI 生成的代码需要 review 吗？怎么约束代码风格？

出现公司：小红书AI全栈、CVTE技术面、小红书PE、CVTE一面（5家） 答： 一定要 review。AI 生成的代码看起来工整，但可能有隐含 bug——边界条件没处理、多线程竞态、内存泄漏。我会仔细审查逻辑，特别是异常路径。 约束代码风格：在提示词里明确要求遵循什么规范（比如 Google C++ Style Guide），命名用驼峰还是下划线，注释风格等。还可以配置 ESLint/Prettier/clang-format 等工具自动格式化。多人协作引入 AI 时，重点是统一提示词模板，确保 AI 输出风格一致，再配合代码审查流程。

⭐⭐⭐ 短期和长期记忆怎么区分/转换？

出现公司：CVTE技术面（2家） 答： 短期记忆就是当前对话的上下文窗口内的内容，容量有限，对话结束就没了。长期记忆是持久化存储的，跨会话保留。 转换方式：对话过程中提取关键信息（比如用户偏好、项目架构决策），写入外部存储（文件、数据库、向量库）。下次新对话开始时，从长期记忆中检索相关内容注入上下文。也可以定期让 AI 对长对话做摘要，把摘要存入长期记忆。

⭐⭐⭐ 你了解 LLM 的上下文窗口吗？怎么实现会话间信息传递？

出现公司：剪映一面、剪映二面（3家） 答： 上下文窗口是模型一次能处理的最大 token 数，比如 GPT-4 是 128K，Claude 是 200K。超出窗口的内容会被截断或遗忘。 会话间信息传递：把上一个会话的关键输出保存下来（存文件或数据库），新会话开始时把这些信息作为上下文注入提示词。更高级的做法是用向量数据库存历史对话，新会话时用语义检索找到相关的历史片段注入。 Agent 自带的压缩策略：一般是滚动窗口（保留最近 N 轮对话）+ 自动摘要（把旧对话压缩成摘要）+ 关键信息提取（提取实体和决策存到结构化存储）。

⭐⭐⭐ Whisper 的原理是什么？怎么识别？

⭐⭐⭐ 你 AI 设计的双模式有什么意义？上下文隔离有什么优势？

出现公司：小红书AI全栈（2家） 答： 双模式是指"对话模式"和"执行模式"。对话模式只做问答和方案讨论，不直接改代码；执行模式才真正生成和修改代码。意义：对话模式让 AI 先理解需求、讨论方案，确认方案合理后再切执行模式写代码，避免 AI 不理解需求就乱写。相当于"先想清楚再动手"。 上下文隔离的优势：不同任务用不同会话，避免无关上下文干扰。比如改音视频模块用一个会话，改 AI 模块用另一个，两边的代码上下文不混。好处：AI 不会被无关信息带偏，输出更聚焦；单次上下文更短，AI 理解更准确；出问题好定位是哪个会话引入的。

⭐⭐⭐ 推荐算法为什么以用户为基准？

⭐⭐⭐⭐⭐ 手撕生产者消费者模型

出现公司：小米二面（1家） 答： 
queue<int> q;
mutex mtx;
condition_variable cv;
bool done = false;

// 生产者
void producer() {
    for (int i = 0; i < 100; i++) {
        unique_lock<mutex> lock(mtx);
        q.push(i);
        cv.notify_one();  // 通知消费者
        lock.unlock();
    }
    {
        lock_guard<mutex> lock(mtx);
        done = true;
        cv.notify_all();  // 通知所有消费者退出
    }
}

// 消费者
void consumer() {
    while (true) {
        unique_lock<mutex> lock(mtx);
        cv.wait(lock, []{ return !q.empty() || done; });
        if (q.empty() && done) break;  // 退出条件
        int val = q.front();
        q.pop();
        lock.unlock();
        // 处理 val
    }
}


退出逻辑关键：用 done 标志 + notify_all，消费者被唤醒后检查 done，队列为空且 done 就退出。

⭐⭐⭐⭐ 二叉树的层序遍历（递归 + 非递归）

出现公司：拼多多客户端1面、小红书PE、百度移动端（4家） 答： 非递归：用队列，根节点入队，循环取出队首，访问，左右子节点入队。O(n)。 递归：传入层数参数，把每层的节点存到 vector<vector<int>> 对应位置。 
// 非递归
vector<vector<int>> levelOrder(TreeNode* root) {
    vector<vector<int>> res;
    if (!root) return res;
    queue<TreeNode*> q;
    q.push(root);
    while (!q.empty()) {
        int size = q.size();
        vector<int> level;
        for (int i = 0; i < size; i++) {
            TreeNode* node = q.front(); q.pop();
            level.push_back(node->val);
            if (node->left) q.push(node->left);
            if (node->right) q.push(node->right);
        }
        res.push_back(level);
    }
    return res;
}

⭐⭐⭐⭐ 判断链表是否有环 / 找到环入口

出现公司：百度移动端、深圳飞易通（3家） 答： 快慢指针：慢指针走一步，快指针走两步。如果有环，快指针一定会追上慢指针（在环里转圈迟早相遇）。如果无环，快指针先到 nullptr。 找环入口：相遇后，让一个指针从头开始，另一个从相遇点开始，两个都走一步，再次相遇的点就是环入口。数学证明：设头到入口距离 a，入口到相遇点 b，相遇点到入口 c，快指针走了 a+b+b+c，慢指针走了 a+b，快是慢的两倍，所以 a+b+c = b → a = c。

⭐⭐⭐⭐ 无重复字符的最长子串

出现公司：中金所、小米一面（3家） 答： 滑动窗口。用左右指针维护一个不重复的窗口，用一个 set 或 map 记录窗口内的字符。右指针扩展，遇到重复字符就移动左指针直到无重复。O(n)。 
int lengthOfLongestSubstring(string s) {
    unordered_set<char> st;
    int left = 0, res = 0;
    for (int right = 0; right < s.size(); right++) {
        while (st.count(s[right])) {
            st.erase(s[left++]);
        }
        st.insert(s[right]);
        res = max(res, right - left + 1);
    }
    return res;
}

int josephus(int n, int k) {
    int res = 0;  // f(1, k) = 0
    for (int i = 2; i <= n; i++) {
        res = (res + k) % i;
    }
    return res;  // 0-indexed
}

出现公司：拼多多一面（1家） 答： 用堆 + 哈希表。维护一个大小为 20 的小顶堆，堆顶是 top20 中最少的。每次点赞更新商品的赞数，如果商品已经在堆里，更新后调整堆；如果不在堆里但赞数超过堆顶，弹出堆顶加入新商品。但 10 亿商品全扫描太慢，加一层优化：用哈希表存所有商品的赞数，堆只维护 top20。更大规模可以用分片——把商品按 ID 分到多台机器，每台维护本地 top20，再合并全局 top20。如果要求实时性，可以用 Redis 的 Sorted Set，ZADD 更新分数，ZREVRANGE 取 top20，O(log N)。

⭐⭐⭐ 海量玩家积分榜，用什么排序算法？

⭐⭐⭐ 线程安全的队列怎么设计？

出现公司：影笑一面（1家） 答： 用互斥锁保护队列操作。入队：加锁 → push → 解锁 → 通知条件变量。出队：加锁 → 等待条件变量（队列非空）→ front + pop → 解锁。要注意虚假唤醒——用 while 循环检查条件，不用 if。如果队列是环形缓冲区（固定大小），可以用数组 + 头尾指针，满了就阻塞生产者。更高性能的方案：无锁队列，用 CAS 原子操作实现（如 boost::lockfree::queue），但实现复杂，一般场景用锁就够了。 
template<typename T>
class ThreadSafeQueue {
    queue<T> q;
    mutex mtx;
    condition_variable cv;
public:
    void push(T val) {
        lock_guard<mutex> lock(mtx);
        q.push(val);
        cv.notify_one();
    }
    T pop() {
        unique_lock<mutex> lock(mtx);
        cv.wait(lock, [this]{ return !q.empty(); });
        T val = q.front();
        q.pop();
        return val;
    }
};

⭐⭐⭐ 设计功能时遇到并发需求，怎么选择互斥和同步技术？

出现公司：影笑一面（1家） 答： 看场景：如果只是保护共享资源不被同时访问，用互斥锁（mutex）。如果是生产者-消费者模式，生产者生产数据通知消费者消费，用条件变量（condition_variable）。如果是一个线程等另一个线程完成，用 promise/future 或 join。如果是多读少写，用读写锁（shared_mutex），读可以并发，写独占。如果是简单计数器或标志位，用原子操作（atomic），不加锁性能最好。如果自旋等待时间很短（内核切换成本 > 等待时间），用自旋锁（spinlock）。选择原则：能用原子就不用锁，能用读写锁就不用互斥锁，等待时间长用互斥锁，等待极短用自旋锁。

⭐⭐⭐⭐ KMP 字符串匹配算法

出现公司：PDF面经总结（3家） 答： KMP 核心：利用已匹配的信息，跳过不必要的比较。预处理模式串生成 next 数组（前缀表），next[i] 表示模式串 [0..i] 的最长相同前后缀长度。匹配失败时不用回退主串指针，而是用 next 数组把模式串指针跳到前缀的下一个位置。 next 数组计算：对于模式串 "abab"，next = [0,0,1,2]。next[2]=1 因为 "aba" 的前缀 "a" 和后缀 "a" 相同。next[3]=2 因为 "abab" 的前缀 "ab" 和后缀 "ab" 相同。 时间复杂度：预处理 O(m)，匹配 O(n)，总共 O(n+m)。暴力匹配是 O(nm)。

⭐⭐⭐ 最长公共子序列（LCS）

出现公司：PDF面经总结（2家） 答： 动态规划：dp[i][j] 表示 text1 前 i 个字符和 text2 前 j 个字符的 LCS 长度。如果 text1[i-1] == text2[j-1]，dp[i][j] = dp[i-1][j-1] + 1；否则 dp[i][j] = max(dp[i-1][j], dp[i][j-1])。 时间 O(mn)，空间 O(mn) 可优化为 O(min(m,n))（滚动数组）。 如果要输出 LCS 字符串本身，回溯 dp 数组：从 dp[m][n] 开始，如果字符相等则加入结果并向左上走，否则往较大方向走。 子序列 vs 子串：子序列不要求连续，子串要求连续。最长公共子串用 dp[i][j] = dp[i-1][j-1]+1（不等时归零），取 dp 数组最大值。

⭐⭐⭐ 背包问题（0-1背包、完全背包）

出现公司：PDF面经总结（2家） 答： 0-1 背包：N 个物品每个只能选一次，容量 W 的背包，求最大价值。dp[i][j] 表示前 i 个物品容量 j 的最大价值。dp[i][j] = max(dp[i-1][j], dp[i-1][j-w[i]] + v[i])。空间优化为一维：dp[j] = max(dp[j], dp[j-w[i]] + v[i])，逆序遍历 j 防止重复选取。 完全背包：每个物品可以选无限次。状态转移一样，但正序遍历 j，因为可以重复选。dp[j] = max(dp[j], dp[j-w[i]] + v[i])。 区别：0-1 背包逆序保证每个物品只选一次；完全背包正序允许重复选。

⭐⭐⭐ 最短路径算法（Dijkstra / Floyd）

出现公司：PDF面经总结（2家） 答： Dijkstra：单源最短路径，非负权图。贪心策略：维护已确定最短路径的集合 S，每次从不在 S 的顶点中选距离源点最近的加入 S，更新其邻居的距离。用优先队列（小顶堆）优化到 O(E log V)。不能处理负权边（用 Bellman-Ford）。 Floyd：多源最短路径，可以处理负权但不能有负环。动态规划：dp[i][j] 表示 i 到 j 的最短距离，枚举中间点 k：dp[i][j] = min(dp[i][j], dp[i][k] + dp[k][j])。时间 O(V³)，适合稠密图或需要查询任意两点间最短路的场景。

⭐⭐⭐ 最小生成树（Kruskal / Prim）

出现公司：PDF面经总结（2家） 答： Kruskal：按边权从小到大排序，依次选边，如果边的两端不在同一集合（用并查集判断）就加入生成树。时间 O(E log E)。适合稀疏图（边少）。 Prim：从一个顶点开始，每次选连接已选集合和未选集合的最小权边。用优先队列优化到 O(E log V)。适合稠密图（边多）。 区别：Kruskal 是边导向（排序边），Prim 是点导向（扩展点）。

⭐⭐⭐ 拓扑排序（Kahn 算法）

出现公司：PDF面经总结（2家） 答： 拓扑排序用于有向无环图（DAG），把所有顶点排成线性序列使得每条边 u→v 中 u 在 v 前面。 Kahn 算法（BFS）：1）计算每个顶点的入度。2）把入度为 0 的顶点入队。3）取出队首顶点加入结果，把它所有邻居的入度减 1，入度变 0 就入队。4）重复直到队空。如果结果顶点数 < 总顶点数，说明有环。 应用：任务调度（先修课程、编译依赖）、检测有向图是否有环。

⭐⭐⭐ 布隆过滤器原理及应用

出现公司：PDF面经总结（2家） 答： 布隆过滤器（Bloom Filter）：一种概率型数据结构，用于判断元素是否在集合中。特点：可能有假阳性（说在但实际不在），但不会有假阴性（说不在就一定不在）。 原理：用 k 个哈希函数把元素映射到 m 位的位数组上，设置对应位为 1。查询时对元素做 k 次哈希，如果所有对应位都是 1 则"可能存在"，如果有任何一位是 0 则"一定不存在"。 应用：缓存穿透防护（请求前先查布隆过滤器，不存在就不查数据库）、垃圾邮件过滤、URL 去重（爬虫）。Redis 中可以用 RedisBloom 模块实现。 不能删除：因为多个元素可能共享同一位，删除会把其他元素也删掉。Counting Bloom Filter 用计数器代替位可以支持删除。

⭐⭐⭐ 滑动窗口最大值（单调队列）

出现公司：PDF面经总结（2家） 答： 问题：数组 nums 和窗口大小 k，窗口从左到右滑动，返回每个窗口的最大值。 单调队列解法：维护一个双端队列存下标，保证队列内对应元素从大到小单调。遍历数组：1）队首下标超出窗口范围就弹出。2）新元素比队尾元素大就弹出队尾（维护单调性）。3）新元素入队。4）窗口形成后（i >= k-1），队首就是当前窗口最大值。 时间 O(n)——每个元素最多入队出队各一次。空间 O(k)。 
vector<int> maxSlidingWindow(vector<int>& nums, int k) {
    vector<int> res;
    deque<int> dq;
    for (int i = 0; i < nums.size(); i++) {
        if (!dq.empty() && dq.front() <= i - k) dq.pop_front();
        while (!dq.empty() && nums[dq.back()] <= nums[i]) dq.pop_back();
        dq.push_back(i);
        if (i >= k - 1) res.push_back(nums[dq.front()]);
    }
    return res;
}

⭐⭐⭐ 前缀和与差分数组

出现公司：PDF面经总结（2家） 答： 前缀和：prefix[i] = arr[0] + arr[1] + ... + arr[i-1]，区间 [l, r) 的和 = prefix[r] - prefix[l]。预处理 O(n)，查询 O(1)。适用于频繁查询区间和。 差分数组：diff[i] = arr[i] - arr[i-1]，对区间 [l, r] 加 val 只需 diff[l] += val, diff[r+1] -= val，还原时前缀和。预处理 O(n)，区间更新 O(1)。适用于频繁区间增减操作。

⭐⭐⭐ 线段树

出现公司：PDF面经总结（2家） 答： 线段树：支持区间查询和单点/区间更新的树形数据结构。每个节点存储一个区间的聚合信息（和、最大值、最小值）。查询和更新 O(log n)。 构建：根节点表示 [0, n-1]，左子 [0, mid]，右子 [mid+1, n-1]。叶子节点存单个元素。 区间更新用懒标记（Lazy Propagation）：更新区间时如果当前节点区间完全被覆盖，只更新当前节点并打懒标记，不下传；下次访问子节点时才下传懒标记。这样区间更新也是 O(log n)。 应用：区间求和、区间最值、区间染色。比前缀和更灵活（支持更新），比树状数组功能更全（支持区间更新）。

⭐⭐⭐ 二叉树最近公共祖先（LCA）

出现公司：PDF面经总结（2家） 答： 递归解法：从根开始递归，如果当前节点是 p 或 q 就返回当前节点。左子树递归找 p/q，右子树递归找 p/q。如果左右子树都返回非空，说明 p 和 q 分布在两侧，当前节点就是 LCA。如果只有一侧返回非空，说明 LCA 在那一侧。 时间 O(n)，空间 O(h)（递归栈）。 
TreeNode* lowestCommonAncestor(TreeNode* root, TreeNode* p, TreeNode* q) {
    if (!root || root == p || root == q) return root;
    TreeNode* left = lowestCommonAncestor(root->left, p, q);
    TreeNode* right = lowestCommonAncestor(root->right, p, q);
    if (left && right) return root;
    return left ? left : right;
}

⭐⭐⭐ O(1) 时间插入、删除、获取随机元素

出现公司：PDF面经总结（2家） 答： 用数组 + 哈希表。数组存元素，哈希表存值到下标的映射。插入：追加到数组末尾，哈希表记录下标。获取随机：随机生成下标，返回数组对应元素。删除：把要删的元素和数组末尾元素交换，更新哈希表，然后 pop 末尾——O(1) 删除。 关键：不能直接从数组中间删除（O(n)），要交换到末尾再删。

⭐⭐⭐ 二维数组二分查找（杨氏矩阵）

出现公司：PDF面经总结（1家） 答： 杨氏矩阵：每行从左到右递增，每列从上到下递增。查找目标值。 从右上角开始：如果当前值 > 目标，列左移（去掉当前列）；如果当前值 < 目标，行下移（去掉当前行）。时间 O(m+n)。 不能从左上角开始（左上角是最小值，无法决定方向）。

⭐⭐⭐ 多线程安全 LRU / LRU 缓存污染（LFU）

出现公司：PDF面经总结（2家） 答： 多线程安全 LRU：在哈希表 + 双向链表基础上，对每个操作加互斥锁。读操作也要加锁（因为要移动节点到头部）。更高性能：用分段锁（把缓存分成多个段，每段独立加锁），或用读写锁（读多写少场景）。 LRU 缓存污染：偶尔被访问一次的冷数据把热数据挤出缓存。解决：LFU（Least Frequently Used）按访问频率淘汰，不淘汰最近最少而是最少访问的。LFU 用两个哈希表（频率表 + 频率到节点的映射）。或用 LRU-K（要求访问 K 次才进入缓存）。 Redis 淘汰策略：allkeys-lru（LRU）、allkeys-lfu（LFU）、volatile-lru（只淘汰有过期时间的）等。

⭐⭐⭐ 快排优化（随机 pivot、三路快排）

出现公司：PDF面经总结（2家） 答： 快排最坏情况 O(n²) 出现在已排序/逆序数组（每次 pivot 是最值）。优化： 1. 随机 pivot：随机选一个元素做 pivot，避免最坏情况。期望 O(n log n)。 2. 三路快排：把数组分成 < pivot、= pivot、> pivot 三部分，对 < 和 > 部分递归。适合有大量重复元素的数组。 3. 小数组用插入排序：当子数组长度 < 某阈值（如 16）时用插入排序，减少递归开销。 4. 尾递归优化：对较长的子数组递归，较短的用循环。 
// 三路快排核心
int lt = lo, gt = hi, i = lo + 1;
while (i <= gt) {
    if (nums[i] < pivot) swap(nums[lt++], nums[i++]);
    else if (nums[i] > pivot) swap(nums[i], nums[gt--]);
    else i++;
}
// 递归 [lo, lt-1] 和 [gt+1, hi]

⭐⭐⭐ 二分查找变种

出现公司：PDF面经总结（2家） 答： 标准二分查找：找目标值位置，找不到返回 -1。 变种1（找第一个等于目标）：nums[mid] >= target 时 right = mid，最后检查 nums[left] 是否等于 target。 变种2（找最后一个等于目标）：nums[mid] <= target 时 left = mid，最后检查 nums[right]。 变种3（找第一个大于等于目标）：lower_bound，nums[mid] >= target 时 right = mid。 变种4（找第一个大于目标）：upper_bound，nums[mid] <= target 时 left = mid + 1。 关键区别：标准二分找到就返回；变种要继续往左/右找边界，用 left < right 循环且 mid 的取值要避免死循环（mid = left + (right - left) / 2 还是 mid = left + (right - left + 1) / 2）。

⭐⭐⭐ 堆排序与 Top-K 问题

出现公司：PDF面经总结（2家） 答： 堆排序：先建大顶堆（从最后一个非叶子节点开始向下调整），然后不断把堆顶（最大值）和末尾交换，缩小堆，再调整。时间 O(n log n)，空间 O(1)，不稳定。 Top-K 问题：求前 K 大用小顶堆（堆大小 K），求前 K 小用大顶堆。遍历数组，比堆顶大就替换堆顶再调整。时间 O(n log K)，空间 O(K)。 也可以用快排的 partition 思想：每次 partition 后如果 pivot 位置等于 K-1 就找到了。平均 O(n)，最坏 O(n²)。

⭐⭐⭐ 图的 DFS / BFS 遍历

出现公司：PDF面经总结（2家） 答： DFS（深度优先）：用栈或递归，沿着一条路走到底再回溯。用 visited 数组避免重复访问。适合连通性判断、拓扑排序、找所有路径。空间 O(h)（h 是深度）。 BFS（广度优先）：用队列，逐层扩展。用 visited 数组避免重复。适合最短路径（无权图）、层序遍历、连通分量。空间 O(w)（w 是最大宽度）。 
// BFS 模板
queue<int> q;
q.push(start);
visited[start] = true;
while (!q.empty()) {
    int node = q.front(); q.pop();

            q.push(neighbor);

    }
}

⭐⭐⭐ 动态规划 / 贪心 / 回溯框架

出现公司：PDF面经总结（3家） 答： 动态规划：重叠子问题 + 最优子结构。自底向上填表或自顶向下记忆化。状态定义 → 状态转移方程 → 初始条件 → 遍历顺序。典型：背包、LCS、最长递增子序列、编辑距离。 贪心：每步选当前最优，不回退。需要证明贪心选择性质（局部最优能推出全局最优）。典型：活动选择、哈夫曼编码、跳跃游戏。不是所有问题都能贪心。 回溯：DFS + 撤销选择。用选择/撤销选择框架遍历所有可能。典型：全排列、组合、子集、N 皇后。剪枝优化（排序后跳过重复、提前终止）。 
// 回溯模板
void backtrack(路径, 选择列表) {

    for (选择 : 选择列表) {
        做选择;
        backtrack(路径, 选择列表);
        撤销选择;
    }
}

Q1 方阵可逆的充分必要条件？

方阵 A 可逆的充要条件是 det(A) != 0（行列式不为零），即 A 是非奇异矩阵。

等价条件包括：① A 的行列式不为零；② A 是满秩矩阵（rank = n）；③ A 的行向量组和列向量组均线性无关；④ AX=0 只有零解；⑤ A 的特征值均不为零；⑥ A 可表示为若干初等矩阵的乘积。

Q2 Phong 和 Blinn-Phong 局部光照模型公式及优缺点？

Phong 模型：光照 = 环境光(Ambient) + 漫反射(Diffuse) + 镜面反射(Specular)

I = I_ambient + k_d * (N·L) * I_light + k_s * (R·V)^n * I_light

其中 R 是光线反射向量，V 是视线方向，N 是法线，L 是光线方向，n 是高光指数。

Blinn-Phong 模型：将 R·V 替换为 N·H，其中 H = normalize(L + V) 是半程向量。

I = I_ambient + k_d * (N·L) * I_light + k_s * (N·H)^n * I_light

优缺点对比：

  • Phong 优点：物理含义直观，反射向量容易理解
  • Phong 缺点：在低光泽度时高光边缘有锯齿，计算反射向量 R 需要额外开销
  • Blinn-Phong 优点：计算更高效（无需算反射向量），高光更圆润自然，在某些角度下更符合物理规律
  • Blinn-Phong 缺点：高光区域通常比 Phong 略大，需要调整指数 n（通常 Blinn-Phong 的 n 设为 Phong 的 2-4 倍以获得类似效果）

Q3 判断数组是否是二叉排序树的后序遍历？

思路：后序遍历的最后一个元素是根节点。数组前半部分是左子树（都小于根），后半部分是右子树（都大于根），递归判断。

bool verifyPostorder(int* seq, int len) {
    if (len <= 1) return true;
    int root = seq[len - 1];
    int i = 0;
    while (i < len - 1 && seq[i] < root) i++; // 左子树
    for (int j = i; j < len - 1; j++) {
        if (seq[j] < root) return false; // 右子树不能有小于根的
    }
    return verifyPostorder(seq, i) &&
           verifyPostorder(seq + i, len - 1 - i);
}

Q4 C++和C语言最大的区别是什么？

C++ 是 C 的超集，主要区别：

  • 编程范式：C 是面向过程，C++ 支持面向对象（封装、继承、多态）和泛型编程（模板）
  • 类型系统：C++ 类型检查更严格，函数原型必须匹配；C 允许隐式声明
  • 关键特性：C++ 有类、虚函数、模板、异常处理、命名空间、引用、运算符重载、STL
  • 内存管理：C 用 malloc/free，C++ 用 new/delete（调用构造/析构函数）
  • const：C 中 const 只是只读变量，C++ 中 const 是真正的常量

Q5 菱形继承是什么？虚表里存了什么？

菱形继承：D 继承 B 和 C，B 和 C 都继承 A，形成菱形结构。导致 A 的成员在 D 中有两份副本，存在二义性。

解决：虚继承。B 和 C 虚继承 A，共享同一个 A 子对象。

虚表内容：虚继承时，虚表存储的是虚基类指针（vbptr），指向虚基类表（vbtable），表中记录虚基类相对于当前位置的偏移量。普通虚函数表（vtable）存储的是虚函数指针。两者是不同的表。

Q6 含虚函数类的sizeof计算

类中有 int a, long b, void func(), virtual void func2()：

  • 需要存储 a（4字节）和 b（8字节，64位下），加上虚函数表指针 vptr（8字节）
  • 普通成员函数不占空间，虚函数通过 vptr 指向虚表
  • 考虑内存对齐：vptr(8) + a(4) + padding(4) + b(8) = 24字节（64位）
  • 如果是子类继承两个父类，会有两个 vptr，大小更大

Q7 const在*左和右的区别？const修饰成员函数？

  • const int* p（const在*左边）：指针指向的内容是常量，不能通过 p 修改值
  • int* const p（const在*右边）：指针本身是常量，不能修改 p 的指向
  • const int* const p：两者都是常量
  • 成员函数后加 const：表示该函数不能修改对象的成员变量（this指针变为 const Type*）。如需修改某个成员，可用 mutable 修饰该变量

Q8 volatile的作用？多线程寄存器是否共享？

volatile：告诉编译器不要对变量做优化（如缓存到寄存器），每次都从内存读取。适用于硬件寄存器映射、信号处理等场景。

多线程寄存器：每个线程有自己独立的寄存器组（CPU 切换线程时保存/恢复上下文），寄存器不共享。但主内存是共享的，volatile 不能保证原子性和可见性（在 C++ 中需要用 std::atomic）。

Q9 构造函数和析构函数哪个可以是虚函数？

析构函数可以是虚函数（推荐在基类中声明虚析构函数），因为多态删除基类指针时能正确调用派生类析构函数，防止内存泄漏。

构造函数不能是虚函数：虚函数调用依赖虚函数表指针 vptr，而 vptr 在构造函数中初始化。构造函数执行前对象还没创建，没有 vptr 可用，所以构造函数不能是虚函数。

Q10 如何使对象只在堆上生成而不在栈上？

将析构函数设为 private 或 protected，这样栈上对象无法自动调用析构函数（编译报错），只能通过 new 在堆上创建。然后提供一个 public 的 destroy() 方法手动释放：

class HeapOnly {
private:
    ~HeapOnly() {}
public:
    static HeapOnly* create() { return new HeapOnly(); }
    void destroy() { delete this; }
};

Q11 智能指针是线程安全的吗？

shared_ptr：引用计数本身是原子的（线程安全），但 读写同一个 shared_ptr 对象不是线程安全的。多个线程同时读同一个 shared_ptr 是安全的，但一个线程写（reset/operator=）另一个线程读是数据竞争。

unique_ptr：独占所有权，不涉及引用计数，但移动操作不是线程安全的。

weak_ptr：lock() 返回一个 shared_ptr，操作是原子的。

如果需要多线程安全访问，应加锁或使用 std::atomic<shared_ptr>（C++20）。

Q12 左值、右值、左值引用和右值引用？

  • 左值：有地址、有名字，可以取地址的表达式。如变量名、解引用
  • 右值：没有持久地址的临时值。如字面量、函数返回值、表达式结果
  • 左值引用：T&，绑定到左值
  • 右值引用：T&&，绑定到右值，用于移动语义和完美转发
  • std::move：将左值强制转换为右值引用，实际上只是类型转换，不移动任何东西
  • 移动构造函数：接收右值引用，窃取资源而非拷贝，提高性能

Q13 设计一个线程安全的单例模式

Meyers' Singleton（C++11 起线程安全）：

class Singleton {
private:
    Singleton() = default;
public:
    static Singleton& getInstance() {
        static Singleton instance; // C++11保证局部static初始化线程安全
        return instance;
    }
    Singleton(const Singleton&) = delete;
    Singleton& operator=(const Singleton&) = delete;
};

这是最推荐的写法。双锁机制（DCLP）在 C++11 之前使用，但存在内存序问题，C++11 后用 std::call_once 或 Meyers' Singleton 更安全。

Q14 int a[10]; &a+1 和 &a[0]+1 分别表示什么？

&a 的类型是 int(*)[10]（指向整个数组的指针），&a+1 跨过整个数组，地址增加 10 * sizeof(int) = 40 字节。

&a[0] 的类型是 int*（指向第一个元素的指针），&a[0]+1 只移动一个元素，地址增加 sizeof(int) = 4 字节。

Q15 成员函数后面加const的含义和作用？

表示该函数不会修改对象的状态（const 成员函数）。this 指针类型变为 const ClassName*，函数内不能修改非 mutable 的成员变量。const 对象只能调用 const 成员函数。作用是增强代码安全性，防止意外修改。

Q16 求链表倒数第k个节点

快慢指针法：快指针先走 k 步，然后快慢指针同时走，快指针到末尾时慢指针即为倒数第 k 个。

ListNode* findKthFromEnd(ListNode* head, int k) {
    ListNode *fast = head, *slow = head;
    for (int i = 0; i < k; i++) {
        if (!fast) return nullptr;
        fast = fast->next;
    }
    while (fast) {
        fast = fast->next;
        slow = slow->next;
    }
    return slow;
}

Q17 x & (x-1) 的作用是什么？

x & (x-1) 会消除 x 二进制表示中最低位的 1。循环执行直到 x 为 0，执行次数就是 x 中 1 的个数。

int count = 0, x = 981;
while (x) {
    count++;
    x = x & (x - 1);
}
// count = x 二进制中 1 的个数

Q18 大数相加（手撕代码）

用字符串模拟大数加法，从低位到高位逐位相加，处理进位：

string addStrings(string a, string b) {
    int i = a.size() - 1, j = b.size() - 1, carry = 0;
    string result;
    while (i >= 0 || j >= 0 || carry) {
        int sum = carry;
        if (i >= 0) sum += a[i--] - '0';
        if (j >= 0) sum += b[j--] - '0';
        carry = sum / 10;
        result = char(sum % 10 + '0') + result;
    }
    return result;
}

Q19 100万个数字找出最大的10个

最小堆（优先队列）：维护一个大小为 10 的最小堆。遍历每个数字，如果比堆顶大则替换。时间复杂度 O(N·logK)，K=10。

priority_queue<int, vector<int>, greater<int>> pq; // 最小堆
for (int num : nums) {
    if (pq.size() < 10) pq.push(num);
    else if (num > pq.top()) { pq.pop(); pq.push(num); }
}

也可用快速选择法（partition），平均 O(N)，但会修改原数组。

方法1：洗牌算法（Fisher-Yates）：对参与者数组随机洗牌，取第一个为中奖者。每个位置等概率，O(n)。

for (int i = n - 1; i > 0; i--) {
    int j = rand() % (i + 1);
    swap(arr[i], arr[j]);

Q21 有父类、组合类时构造函数调用顺序？

构造顺序：基类 → 成员对象 → 自身。

  1. 先调用基类的构造函数（按继承声明顺序）
  2. 再调用成员对象的构造函数（按成员声明顺序）
  3. 最后执行自身构造函数体

析构顺序完全相反：自身 → 成员对象 → 基类。

Q22 判断大小端并实现字节序转换函数

判断方法：将 int 的地址转为 char*，读取第一个字节。值为低字节则为小端。

bool isLittleEndian() {
    int x = 1;
    return *(char*)&x == 1;
}

大端转本机字节序（类似 ntohl）：

uint32_t bigToHost(uint32_t val) {
    return ((val >> 24) & 0xFF) |
           ((val >> 8) & 0xFF00) |
           ((val << 8) & 0xFF0000) |
           ((val << 24) & 0xFF000000);
}

Q23 判断long型数是否是2^n，要求O(1)

2 的幂的二进制只有一个 1，用 x > 0 && (x & (x-1)) == 0 即可判断：

bool isPowerOfTwo(long n) {
    return n > 0 && (n & (n - 1)) == 0;
}

Q24 单例模式有哪几种写法？双锁机制有什么问题？

常见写法：① 饿汉式（类加载即初始化）；② 懒汉式（延迟初始化）；③ Meyers'（局部静态变量，C++11 线程安全）；④ 双锁机制（DCLP）。

双锁机制的问题：

  • 在 C++11 之前，DCLP 存在内存序问题：分配内存和构造对象的顺序可能被编译器重排，导致其他线程读到未完全构造的对象
  • 需要用内存栅栏或 std::atomic 来保证正确性
  • C++11 后推荐使用 Meyers' Singleton（局部 static 变量），标准保证线程安全且无锁

Q25 为什么用_beginthreadex而不用CreateThread？

Windows 下 CreateThread 创建的线程中，如果使用了 C 运行时库（如 malloc、printf、errno 等），会导致内存泄漏或状态不一致。因为 CRT 需要通过 _beginthreadex 初始化线程的 tiddata 结构（用于管理 per-thread 的 CRT 状态）。_beginthreadex 内部调用 CreateThread，但额外做了 CRT 初始化。

Q26 信号量和互斥锁的区别？设计一个信号量类

互斥锁：二元信号量，只有 0 和 1，用于互斥访问。加锁的线程必须解锁。

信号量：计数器，允许多个线程同时访问资源。可以由其他线程唤醒。

信号量实现：

class Semaphore {
    int count;
    mutex mtx;
    condition_variable cv;
public:
    Semaphore(int n = 0) : count(n) {}
    void wait() {
        unique_lock<mutex> lk(mtx);
        cv.wait(lk, [this]{ return count > 0; });
        count--;
    }
    void signal() {
        unique_lock<mutex> lk(mtx);
        count++;
        cv.notify_one();
    }
};

Q28 如何把多媒体播放器做成边下边播？

核心思路：将播放和下载解耦，用环形缓冲区管理数据：

  • 下载线程：持续从网络读取数据写入环形缓冲区，当缓冲区满时等待
  • 播放线程：从缓冲区读取数据进行解码播放，当缓冲区不足时等待
  • 同步机制：用条件变量 + 互斥锁控制缓冲区读写，避免空读和满写
  • 预缓冲：开始播放前先缓冲一定数据（如 1-2 秒），后续边播边下
  • 码率自适应：根据下载速度动态调整视频质量，避免缓冲区耗尽

在 VA 项目中，HTTP 渐进式流服务器支持 Range 请求，客户端可以边下载边播放，PacketQueue 作为缓冲区。

Q29 FFmpeg解码时音视频不同步怎么解决？

音视频同步方案：

  • 以音频时钟为主时钟：音频用 SDL 回调按采样率播放，天然匀速
  • 视频追赶音频：每帧视频显示前比较当前 pts 与音频时钟，视频快则延迟显示，视频慢则丢帧（跳过非关键帧）
  • pts/dts：利用 FFmpeg 的 packet.pts 和 frame.pts 作为时间戳，换算到同一时间基
  • 具体实现：音频回调中更新 audio_clock，视频线程用 av_diff = video_pts - audio_clock 判断同步状态，diff > 阈值则等待，diff < -阈值则丢帧

在 VA 项目中，以音频为基准时钟，视频帧通过比较 pts 与音频时钟决定显示时机或丢帧。

Q30 TCP为什么是三次握手？两次行不行？

三次握手的原因：双方都需要确认对方的收发能力正常。

  • 第一次：客户端→服务端 SYN，服务端确认客户端发送正常
  • 第二次：服务端→客户端 SYN+ACK，客户端确认服务端收发正常
  • 第三次：客户端→服务端 ACK，服务端确认客户端接收正常

两次不行：如果只有两次，服务端发送 SYN+ACK 后就认为连接建立，但无法确认客户端是否收到了自己的 SYN+ACK。如果客户端之前的 SYN 延迟到达，服务端会误建连接浪费资源。三次握手可以防止历史失效连接初始化。

Q31 手写memcpy函数（注意地址重叠）

地址重叠时需要从后向前拷贝（当 src < dst），避免覆盖未读数据：

void* myMemcpy(void* dst, const void* src, size_t n) {
    char* d = (char*)dst;
    const char* s = (const char*)src;
    if (d < s) {
        for (size_t i = 0; i < n; i++)
            d[i] = s[i];
    } else {
        for (size_t i = n; i > 0; i--)
            d[i - 1] = s[i - 1];
    }
    return dst;
}

Q32 判断两棵二叉树是否相似（可左右旋转得到）

两棵树相似：通过交换任意节点的左右子树能变得相同。递归判断：要么两棵树相同，要么交换一棵的左右子树后相同。

bool isSimilar(TreeNode* a, TreeNode* b) {
    if (!a && !b) return true;
    if (!a || !b) return false;
    if (a->val != b->val) return false;
    return (isSimilar(a->left, b->left) &&
            isSimilar(a->right, b->right)) ||
           (isSimilar(a->left, b->right) &&
            isSimilar(a->right, b->left));
}
